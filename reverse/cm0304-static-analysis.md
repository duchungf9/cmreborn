# Championship Manager 03/04: static match-engine notes

## Scope and target

These are partial static observations from the user-provided Windows release. The inspected executable is PE32 x86, version 4.1.0.0, SHA-256 `f5963ebd6c9df918b9e630402a3bed6a64357f7ff62b9a6d2a6b5d5234bd9b7a`. Addresses below are virtual addresses from the executable image. They have not been validated against other releases.

This is not a 100% reconstruction. Decision weights, most attribute effects, several helper predicates, and the full ball/shot model remain unresolved. The HTML demo deliberately labels inferred behavior.

## Observed action-state flow

- The selection routine beginning at `0x9234A0` writes an action identifier into `[object + 0x8CC]`. An action-processing routine begins near `0x92DF20`.
- In one on-ball arbitration block of `0x9234A0`, the selector adjusts five local candidate values (`local_74`, `local_c8`, `local_84`, `local_a8`, `local_a4`) with `0x8BCA50(-5, 5)` when each is greater than `5`; that helper returns `min + Random(max-min)`, so the adjustment is `-5..4`. It selects `202` (`ME_TURN_ON_BALL`) when `local_74` is positive and below the other four values (the last comparison is `local_a4 <= local_74`). If that branch does not win, it selects `203` (`ME_HOLD_UP_BALL`) when adjusted `local_84` is positive and below `local_c8`, `local_a8`, and `local_a4` (again `local_a4 <= local_84`). Both branches set the movement target to the player's current coordinates; `202` uses movement flags selected from geometry/state gates (`0x80`, `0x100`, `0x80000`, or `0x200000`), while `203` uses `0x10`. A `203` choice is changed to `212` (`ME_GK_DROP_BALL_FOR_DISTRIBUTION`) on a separate goalkeeper flag/state gate, which also clears `[player + 0x8AD]`. This verifies part of the arbitration and tie-jitter behavior, but the candidate values' tactical meanings and their input weights are still unknown.
- In the run-with-ball path, the code compares the absolute x and y target deltas with `10`. It selects action `201` when both are strictly below `10`; otherwise it selects `200`. The source field units have not been mapped to metres.
- Other constant writes in the same selector confirm branches for `204` (`ME_WAIT_TO_FIND_SET_PIECE_ACTION`), `208` (`ME_TAKE_A_DIVE`), `212` (`ME_GK_DROP_BALL_FOR_DISTRIBUTION`), `213` (`ME_ATTEMPT_TO_ROUND_KEEPER`), and `1000` (`ME_GK_USE_SIX_SECONDS`). Action `204` is an early exit when `([player + 0x9C4] & 0x780) != 0` and current match counter `[match + 0xB0] < [player + 0x9C8]`; it stores the current counter at `+0x944` and restores the entry value of `[player + 0x9BC]`. The meaning of mask `0x780` and the deadline's units remain unknown. The `208` branch is now mapped further: it requires player flag bit `1` at `+0x9C4`, a false result from `0x5AB230`, `[player + 0x988] < [match + 0xB0]`, then three separate `Random(5000)` draws greater than candidates `local_a8`, `local_c8`, and `local_a4`. It next requires `Random(200) < Random([player + 0x54] + 50)`, and a later random gate derived from `[player + 0x35C]^3 / 25 + 5`; context flags can add `local_78` or randomize that gate. One success path also requires a random draw below `local_b8`; fallback paths compare `[player + 0x9BC]` with `RandomRange(-200,100)` (the helper's actual range is `-200..99`), compare `[player + 0x9BC] - 2*local_b8` with `100`, or require `0x8FA6C0` and `[player + 0x9BC] - local_b8 < 0`. On selection it writes action `208`, targets the player's current coordinates, sets `+0x8C4=-1`, `+0x8C8=-1000`, and `[player + 0x8D4]=[match + 0xB0]`. Several compared fields and context helpers are still unnamed, so this recovers a gate structure and output state rather than the underlying attribute model.
- The `213` (`ME_ATTEMPT_TO_ROUND_KEEPER`) branch is reached when local candidate `local_c8` is positive and beats `local_a4` and `local_a8`, and the previously derived candidate target passes its `local_3d` gate. That target gate starts only when `[player + 0x9C1]` is set, `local_ba` is clear, and `local_b8 < 60`; it then compares a `Random(25000) / max(0x8E9890(),1)` value with a random bound derived from `([signed_byte(player+0x818)]^2 / 20) * [player+0xBD0] * [player+0x348]`, and requires `[local_60] < 20`. On its target-building path, it takes a heading from the side-indexed object via `0x8C3280`, offsets it by `+50` or `-50`, uses magnitude `max(50, local_c)`, and converts that vector with `0x8C3810/0x8C3850`. Targets with y below `20` or above `[player + 0x78]-20` are rejected. A further gate accepts when `[match + 0x6] < 218`, `local_78 == 0`, or the circular heading difference is at most `60 - distance/10`; otherwise it restores the prior candidate. A selected target is written to `+0x8BC/+0x8C0`, movement mode `0x410` is set, `(local_98 - 20) * 15 + [player + 0x9BC]` is stored in `+0x8C8`, and the `0x8BC3C0` estimate goes to `+0x8C4`. Helper `0x8ECDF0` reads a side-indexed object pointer at `[player + 0x68] + (0x108FB - (char)[player + 0x74]) * 4`; when non-null, that object's field `+0x830` is copied to player `+0x8DE`. The action label suggests the object is the keeper, but its role is not established by this pointer expression alone; the meanings of `local_c8`, `local_98`, `[player + 0x9BC]`, and several geometry fields remain unresolved.
- All three observed writes of `1000` (`ME_GK_USE_SIX_SECONDS`) share a common output setup: movement mode `2`, `+0x8C8=200`, `+0x8D0=[match + 0x423D8] + 48`, and `+0x8C4` from helper `0x8BC4B0`. The target x uses `[player + 0x80]`; target y is normally `60` or `[player + 0x78]-60` according to side, with a `150` offset on one context path. One branch also updates team state byte `+0x570`. The action label is recovered, but the exact trigger combination and the units represented by the `+48` timer and score remain unresolved.
- The selector's delivery helper at `0x9160F0` creates target geometry for several queued ball actions. In its keeper-flag path (`[player + 0x8AF] != 0`), it generates a bounded launch distance, an angle around the player heading, and a target through `0x8C3810/0x8C3850`; one branch writes action `110` (`ME_HEADED_CLEARANCE`) or `112` (`ME_HEADER_INTO_AREA`) from a one-bit branch flag. A separate construction path writes `107` (`ME_CLEARANCE`). The helper also copies the queued action at `[match + 0x15C]` into `[player + 0x8CC]` after an event gate. It tests geometry against pitch bounds and player/target headings, and applies randomized angle/distance adjustments. The full predicate selecting each action, the meanings of the keeper flag and context fields, and the stored units are not decoded; this is a newly traced delivery branch, not a complete clearance model.
- The run selector also calls shared helper `0x8FE890` (26 direct call sites in the executable). It scans candidate objects under a match context and uses geometry helpers. Its observed return paths produce byte values `0`, `1`, and `2`; the two run-selector branches use opposite zero/nonzero tests before choosing action `205`. Treat it as a tri-state helper whose exact meaning depends on the caller, not a global boolean “success” flag.
- The `0x8FE890` call in that run-selector branch supplies the bearing to the current movement target, zero for two additional arguments, and `60` for a fourth argument. Inside the helper, a bounded draw from `[player + 0xB90] + 5` contributes to a candidate threshold; heading/vector helpers `0x8C3810`, `0x8C3850`, `0x8BC550`, and `0x8C7610` derive geometry used by the checks. It scans the player's team list at `[team + 0x534]` with count `[team + 0x568]`, excludes the current player, and reads teammate time, position, movement deadline (`+0x9C8`), and movement flag (`+0x9CC`). It also writes a derived value to global `0xDA9E74`. These are concrete inputs and side effects, but the three return values still cannot be named as “lane clear”, “receiver free”, or another tactical concept without dynamic validation.
- Caller behavior confirms the return is categorical, not just boolean: at `0x8FFA34`, return `1` reduces a local score by `5`, return `2` reduces it by `15`, and return `0` takes a separate geometry adjustment. Another caller at `0x934EA5` continues down its special branch only for return `2`. Those caller-specific effects still do not identify what the categories mean in match terms.
- In the run-selector branch around `0x9285BC`, the field at `[match + 0x6]` splits behavior at `0xD1` (209); its precise semantic name is unknown. On the `>= 209` side, a nonzero result from `0x8FE890` selects action `205`; zero falls through to the `200/201` target-distance check. On the `< 209` side, the zero/nonzero test is reversed: zero selects `205`, while nonzero proceeds to the `200/201` check. That check is exact: both absolute target deltas must be `< 10` for `201`; all other cases choose `200`. The action-name resolver labels `205` as `ME_PLAY_BALL_AHEAD_AND_RUN_ONTO`. The helper's result remains context-dependent, so this branch alone does not recover the full pass-ahead decision formula.
- The action processor at `0x92DF20` calls `0x8EB4E0` with the current action ID. That helper special-cases IDs `501–510`, writes one of ten associated constants to an output slot, and returns true; other IDs write `100` and return false. These action IDs are named as foul/violent-play events in the resolver, but the meaning of the secondary constants has not been identified.
- At the start of this processor, the current match counter at `[match + 0xB0]` is copied to `[player + 0x8D4]`, then the action ID at `[player + 0x8CC]` is passed to the special-case helper. One bounded random draw uses a bound derived as `[player + 0xB90] + 5`. If `[player + 0x64]` is at least `50` and the action is outside the helper's `501–510` set, this path branches out before the later action work. The meanings of these player fields, the draw's consumer, and the `50` threshold units are not yet established.
- The observed shot path is `0x93181B → 0x94C0D0 → 0x94E980 → 0x94CBB0`. `0x94E980` repeatedly asks `0x94CBB0` for trajectory samples, increments a sample count at `+0x3EE8`, and stores values from `+0x3ED8`. A comparison against `999` bounds the loop to about 1000 samples (indices 0–999). A coefficient helper uses `0x4000` (16384) as a fixed-point scale; the coordinate units and complete trajectory equations are still unresolved.
- The shot-type selection block around `0x92A528` has several directly recoverable priority branches. If bit `0x200` is set in `[player + 0x9C4]`, it draws `Random(10)` and compares it with a local threshold at `[esp + 0x24]`. If the threshold is greater, a second `Random(3)` maps `0 → 312` (`ME_SHOT_TYPE_PENALTY_POWER`), `1 → 313` (`ME_SHOT_TYPE_PENALTY_PLACED`), and `2 → 314` (`ME_SHOT_TYPE_PENALTY_WRONG_WAY`); otherwise it selects `315` (`ME_SHOT_TYPE_PENALTY_DEFAULT`). If bit `0x200` is clear, the high bit of `[player + 0x9C4]` selects `304` (`ME_SHOT_TYPE_FREE_KICK`); otherwise current substate `705` (`ME_DIVE_TO_HEAD_BALL`) selects `309` (`ME_SHOT_TYPE_DIVING_HEADER`); otherwise bit `0x2000` in `[player + 0x9C4]` selects `305` (`ME_SHOT_TYPE_BICYCLE_KICK`). Remaining cases enter the general shot-type selector. The penalty threshold is altered by earlier random and flag-dependent code, so this recovers final branches and random ranges, not the full probability model or broader flag meanings.
- The normal-pass action `100` routes through a branch around `0x92EF36` and calls `0x903840`. That routine copies a 17-word context record from offset `+0x15C` to `+0x118` before related match-context updates.
- The selector also constructs restart/delivery contexts. At `0x929B58` it writes action `108`; a nearby branch writes `106` or `114` to context `+0x15C` according to bit `0x40` in player flags at `+0x9C4`. The embedded labels identify these as halfway clearance, cross into area, and corner. This establishes the state values and a flag-controlled split, but not the full trigger meaning.
- Another branch writes `118` (`ME_THROW_DOWN_LINE`) to the context at `0x929E67`. Before that write, it derives two target components through `0x8BC320`, `0x8BC550`, and the vector helpers `0x8C3810/0x8C3850`; it also fills adjacent context fields and then copies the selected ID into the player's `+0x8CC` action field. Their meanings and units remain unresolved.
- A separate construction branch writes `116` (`ME_GOAL_KICK`) at `0x92A25C`. It forms one target component by adding the result of a bounded helper call supplied with `-200` and `200` to a stored coordinate, copies another coordinate directly, fills additional context fields, then reaches the common action write at `0x92D5F5`. The supplied bounds are observed constants; their interpretation and the target record's field semantics have not been dynamically checked.

## Off-ball movement and interception

The player decision block around `0x93AE98–0x93B17A` contains live off-ball movement branches. It writes the chosen action at `[player + 0x8CC]`, movement target coordinates at `+0x8BC/+0x8C0`, and then joins the shared action path at `0x9468D0`.

- A separate team-state rebuild routine at `0x9603A0` is reached from multiple higher-level update helpers. It walks each side's active-player array at team `+0x4CC` (count byte `+0x528`), keeps eligible players whose state byte `+0x8A6` is `1` and whose flags at `+0x882` do not have bit `1`, and builds one list per side. It sorts both lists with an inline comparator at `0x95DD60`: descending by `2 * [player + 0xBB0] + [player + 0xBE8]`, with `[player + 0x0C]` as a descending tie-break. It pairs equal ranks up to the shorter list, storing reciprocal player pointers in `+0xAF4` and `+0xAF8`. The surrounding routine emits debug strings `Initialised setup_markers` and `Done covering players`; this supports a coverage/marking role for the pairing, while the compared fields and their football meanings remain unknown. The demo's role/distance-based marking targets are still proxies and do not reproduce this native ranking or pair assignment.

- One branch chooses `400` (`ME_MOVE_TO_BALL`). It first checks the match-context pointer at `+0x423F8`, a predicate at `0x8FA560`, team identity, and the values at player `+0x9B8` and match time `+0x64`. When that path is reached before time `20`, it asks `0x911840` for a state and stores the return value; `601` is explicitly treated as a special case. If the branch continues, `0x8C6080` is called with the player and match coordinates, the resulting index selects entries from global tables at `0xDA9E78/0xDA9E7C`, and the target is formed from the match coordinates minus those entries. It sets movement mode `4`. The table contents' semantic names and coordinate scale are unresolved.
- The interception branch calls `0x904840` with flags `0x100A` and output slots for two target coordinates plus an auxiliary value. The helper obtains the trajectory object through `[player + 0x68] + 0x68`, reads its sample base index at `+0x4` and count at `+0x8`, then scans 16-byte records beginning at `+0x58`, from the current match counter (or the next tick when flag `0x20` is clear) up to a context-bounded time. The first three dwords are copied to the caller's x, y, and auxiliary outputs for the selected record; flag-dependent branches inspect the third and fourth dwords. The best-score register starts at `2000`; an eligible candidate replaces it only when its accumulated score is lower. In the ordinary scoring arm the base is Euclidean distance through `0x8C65E0`; mask `0x4` adds absolute x separation from `[player + 0x80]`, while masks `0x1`, `0x2`, and `0x400` add separate context/reach/time adjustments. Other masks apply candidate-time, pitch-side, control-event, and record-metadata filters, though their tactical names are unknown. The selected record's absolute trajectory time is stored separately from the score. The helper's return is mode-dependent: with flag bit `0x2`, a randomized comparison may place a `0x8BC3C0` estimate in it; a no-candidate path with bit `0x8` set returns `-1`; other fallbacks can return a current match-time value. The caller stores this return at `[player + 0x8D0]`, so that field is not a universal trajectory index. In the calling movement branch, another estimate is computed through `0x8BC3C0`/`0x8C0420`, reduced by `2` when `0x8EE780` is true, then compared with the helper return; when match-context `+0x1EC` is not `-1`, the estimate is also bounded by that field. The scoring weights, meanings of several flags, and compared-value units remain partly unresolved.
- The helper's reach filter `0x8BCF50` receives a candidate x/y, its trajectory index, and a mode byte. It computes a distance from the candidate to a heading-indexed offset of the player coordinates, adds a turn cost from two circular heading differences scaled by `15 / min([player + 0x60], 40)`, then divides by `max(candidateTime - [match + 0xB0], 1)`. It returns whether that value is below `10` when the mode is nonzero or below `30` when it is zero. This is a gate used alongside, not a replacement for, the candidate score. The table semantics, threshold units, and complete score weights remain unresolved.
- One input to that comparison is now traced more precisely. `0x8BC3C0` computes `3 * (50 - [player + 0x30]) + 3/2 * ([player + 0x348] - penalty)`, where `penalty` is zero when `[player + 0xC0] <= 1600` and otherwise `(field - 1600) / 20` capped at `10`. If `[match + 0x6] >= 0xD7`, the result is capped at `30`. The caller passes this value with the candidate x/y coordinates and option `4` to `0x8C0420`, a wrapper around `0x8BD030`, then compares that path estimate with the mode-dependent return from `0x904840`. The fields, option, result units, and exact meaning of the return remain unresolved.
- Once a candidate passes those gates, an auxiliary output below `15` chooses `414` (`ME_MOVE_TO_INTERCEPT_BALL`); otherwise it chooses `452` (`ME_MOVE_TO_INTERCEPT_HIGH_BALL`). The target is adjusted using bearing helper `0x8BC550` and the same global side tables, then movement mode `4` is set. The planner also compares the third sample dword with thresholds including `10`, `15`, and `20`, and in one flag-conditioned path rejects records whose fourth dword is at most `15`. The `<15` split and these sample fields are consistent with a height/elevation test, but their exact source-field mapping and units are not proven.
- A separate branch uses predicate `0x8FA660` and helper `0x8C0990`; when its returned value is greater than `-40`, it writes an adjusted target and selects `403` (`ME_MOVE_ONSIDE`) with movement mode `0x10`. This is consistent with the action's embedded label, but the helper result, threshold units, and complete trigger conditions remain unresolved.
- The long movement-maintenance routine beginning at `0x9468F0` revisits states `400/401` and `414/415/452`, compares stored candidate values at `+0x8D0` with match time/counter fields, and can recompute targets through `0x94BF40`, `0x8BBAC0`, and `0x904840`. The same `0x904840` helper is called there with several other flag masks (`0x2065`, `0x20AA`, `0x2025`), showing that target prediction is shared by multiple movement paths. Exact flag meanings and the full update cadence remain unresolved.
- The player-position refresh path is distinct from the ball's 16-byte trajectory samples. `0x919EF0` sets a per-player update deadline at `[match + 0xB0] + duration` in `[player + 0x9C8]`, clears `[player + 0x9CC]`, and calls `0x918460`; when argument bit `1` is set, it also calls `0x8BBA10` and `0x904640`. That helper calls `0x8BBAC0` with the current match counter and output pointers for player fields `+0x48/+0x4C/+0x50/+0x54` and `+0xB8`. `0x8BBAC0` reads a separate 28-byte-stride motion record array at `[entity + 0x14]`: before endpoint time `[entity + 0x34]`, it selects a record using `max(requestedTime - [entity + 0x24], 0)`; at/after that time it outputs endpoint coordinates from `+0x38/+0x3C`. It compares selected x/y with the current x/y and returns a changed flag.
- The corresponding path builder is `0x8BD030`, reached from the movement-target wrapper `0x8C0420` and a convenience wrapper at `0x8BE410`. It derives a heading for the requested x/y through `0x8BC730` when needed, obtains direction components from `0x8C3810/0x8C3850`, and accumulates those components in 14-bit fixed-point steps. The heading difference is folded to the shortest signed turn in the 0–359 heading system. On the path gated by `flags & 0x280180`, requested movement magnitude is scaled by `min(100, field[+0x34C] - floor(abs(turn)*4/9) + 90 + field[+0x344])` percent, then floored at 30. Each generated tick rotates by at most field `+0x60` (with a separate goalkeeper/candidate path that derives a limit from `+0xBD0`), and one loop branch increases the per-tick step magnitude by the integer quotient `(90-min(remainingTurn, (15-field[+0x344])*6))*(field[+0x350]+8)*5/180` until it reaches the requested magnitude. These are exact arithmetic relationships in the decompiled path builder; the three player fields have not been mapped to named attributes, and the flag branches decide when each rule applies. The loop shifts accumulators right by 14 to form integer x/y samples, then copies seven dwords into `[entity + 0x14] + sampleIndex * 0x1C`; it also updates endpoint x/y at `+0x38/+0x3C`, heading at `+0x42`, and path start/end times at `+0x24/+0x34`. Thus movement is represented by a generated, timed list of discrete positions rather than by a render-frame velocity update. Each record stores x/y, a caller-provided byte at `+0x08`, the current step magnitude at `+0x0C`, heading at `+0x10`, and two additional dwords at `+0x14/+0x18` whose uses are not fully mapped. `0x8BBAC0` selects one of those samples by time; interpolation between samples has not been found.
- The native table source for the low-magnitude vector branch is now identified. `0x8CBF40` loads `distance_angle_table.mdt` as 360 headings × 100 magnitudes. Its payload is 36,000 pairs of signed 32-bit components after a 12-byte MDT header. For magnitudes `0–99`, `0x8C3810` and `0x8C3850` index that grid by `heading * 100 + magnitude`; the executable's in-memory component records use a 12-byte stride. Table rows confirm the heading convention: heading 0 points along positive y, 90 along positive x, 180 along negative y, and 270 along negative x. At magnitude `>= 100`, both helpers use a separate per-heading basis and integer scaling by 1/20; the exact source/meaning of that basis is still unresolved. This accounts for the movement-vector inputs without identifying the speed/attribute formula that chooses their magnitude.
- The sample reader is discrete rather than interpolated. Before endpoint time `[entity + 0x34]`, `0x8BBAC0` computes `max(requestedTime - [entity + 0x24], 0)` and reads that 28-byte record directly. It returns x/y plus the record's byte `+0x08`, dword `+0x0C`, word `+0x10`, and dword `+0x14` through caller-provided outputs. At or after endpoint time it returns the stored endpoint x/y at `+0x38/+0x3C` and endpoint metadata. The visible frame smoothing, if any, is outside this sampler; no interpolation inside the native position reader has been found.
- The ball-arrival resolver at `0x913BB0` was decompiled over its full body (`0x913BB0–0x914ADD`). `0x9468F0` calls it at a movement-state timing gate with an output pointer to `[player + 0x8C8]`, then writes the returned action to `[player + 0x8CC]`; the `+0x8C8` value participates in score/threshold calculations, but its field name is unresolved. It samples the ball trajectory at match counter minus `2` through `0x94BF40`, checks `0x8BFA00` with distance argument `250`, and gates on trajectory progress, current movement/action state, player side and match context. One exact intermediate term is `((Random([player + 0x344]) + trunc(3 * signed_byte([player + 0x7BC]) / 2) + Random([player + 0xBE4] + 2)) * [match + 0xA0F2C]) / 100`, using integer arithmetic; its fields and units are not mapped. Later branches use further bounded draws from `[player + 0xBB0] + 2` and `[player + 0xBE0] + 2`, trajectory byte `+0x59`, and match fields `+0x6D8/+0x6DC`. Those gates produce observed codes `600` (`ME_NOT_SAVED`), `800–806` (goalkeeper save/contact outcomes), `3` (`ME_TRY_SAVE_NEXT_TIME_SLICE`), and `0` (no action); `801–806` are individual branches, not one generic save result. The trajectory-byte branch uses numeric bases `100`, `200`, `300`, `400`, or `800` in bounded-random calculations. This is a partially recovered probability/transition path; field meanings, full thresholds, and complete outcome weights remain unresolved.
- A second, broader ball-contact decision routine at `0x911840` (`0x911840–0x913B95`) takes a player and an output-score pointer; `0x913BB0` calls it on several fallback paths. Its early eligibility checks include trajectory end/progress, a current interception candidate on the same side, and player action context. Explicit state returns include `ME_NO_ACTION` (`0`), `ME_TRY_SAVE_NEXT_TIME_SLICE` (`3`), `ME_HANDBALL` (`500`), foul types `501–506`, `ME_FAIL_CONTROL` (`601`), `ME_DEFLECT_BALL` (`700`), `ME_CONTROL_BALL` (`701`), `ME_JUMP_FOR_BALL` (`702`), `ME_INTERCEPT_BALL` (`703`), `ME_PICK_UP_LOOSE_BALL` (`704`), `ME_DIVE_TO_HEAD_BALL` (`705`), `ME_FIRST_TIME_CLEARANCE` (`707`), `ME_SET_FOR_OVERHEAD_KICK` (`708`), and tackle outcomes `900/901`. It initializes and updates the score output separately from the state return, and combines sampled ball position, player/ball geometry, orientation, match context, attributes at several unresolved offsets, and bounded random draws.
- The foul-type helper at `0x904030` is reached from `0x911840` and returns labels `501–506`: shirt tug, obstruction, two-footed tackle, trip, push, or elbow. Its branches compare the players' circular heading difference (notably thresholds `60` and `120`), geometry-helper results from the opponent position and match reference coordinates at `+0x6D0/+0x6D4`, a player state byte at `+0x8AF`, and bounded draws with bounds `2`, `20`, `30`, or `([player + 0xC60] byte + 1) * 1000`. The preceding `0x8FDA10` call updates a player accumulator at `+0xBC8` on some paths and returns an EAX value used by the helper's next comparison; its field semantics and the `+0xC60` byte are unmapped. These are recovered gates and random ranges, not a calibrated foul probability model. The demo still does not execute this native contact/foul path; score weights and stored-field-to-attribute mappings remain open.
- The action processor contains a separate set-piece preparation transition: when `[player + 0x8F4]` is `450` (`ME_STEP_BACK_TO_TAKE_SET_PIECE`), the action at `+0x8CC` is not `204`, a bit in `[player + 0x9C4] & 0x6C0` is set, and `[match + 0xB0] >= [player + 0x34]`, it computes a new position from the match's team reference coordinates and the same `0xDA9E78/0xDA9E7C` tables. It then changes `+0x8F4` to `451` (`ME_STEP_UP_TO_TAKE_SET_PIECE`) and calls movement/update helpers. The bit meanings, clock units, and exact semantics of the adjacent player fields are unresolved.

These branches establish that movement decisions use a predicted ball-path record set and explicit competing reach/index checks. They do not expose the full scoring formula, all action transitions, or a direct mapping from simulation units to field coordinates.

## Ball trajectory state

- The action dispatcher routes `100` (`ME_NORMAL_PASS`) through `0x8BC0D0` and then `0x903840`; several related pass/header/clearance action IDs share that worker. It copies 17 dwords from match `+0x15C..+0x19C` into `+0x118..+0x158`, then calls trajectory initializer `0x94C0D0` and builder `0x94E980` with the outgoing-ball context. The copy maps source `+0x184` to flight `+0x140` (curve input), and source `+0x190` to flight `+0x14C` (designated-player pointer). That pointer is used in event and geometry checks, including side and position comparisons. A concrete producer is the kick-off branch of `0x938F60`, reached under an unresolved `0x8C78A0` predicate and match flag bit `0x400` at `+0x6C8`: it writes match `+0x190` to team `+0x538`, falling back to team `+0x534` if the first pointer is the current player, then sets context action `121` and dispatches it. The meanings of those two team fields and the generic-pass writer/selector remain unresolved. The demo now replays this action at opening kick-off, half-time, and after goals, using a midfield receiver as an explicitly inferred proxy for the unnamed team pointers. After building the path, the worker updates the match's active-player pointer at `+0x42408`, toggles involved players' `+0x8A2` ownership byte, clears the interception-candidate pointer at `+0x423F8`, snapshots current ball coordinates into match `+0x12C..+0x134`, and updates team possession counters. This establishes the pass execution and flight handoff, but not how pass candidates are scored or how path parameters depend on player/tactical attributes.
- `0x94C0D0` initializes a trajectory object from three supplied coordinate values, resets trajectory counters/flags, and copies the match counter at `[match + 0xB0]` into its initial time fields. When there is no explicit source object, a neighboring initializer (`0x94C130`) asks `0x8BBAC0` for a current position based on the match's active ball object before initializing the trajectory.
- `0x94E980` builds the time/position samples. It stores position records at 16-byte strides beginning at object `+0x58`, tracks sample metadata around `+0x3ED4/+0x3ED8`, and increments a count at `+0x3EE8`. A loop bounds its sample index to `0..999`; `0x94CBB0` also guards against an index reaching `1000`.
- The base segment initializer `0x94C500` sets 14-bit x/y accumulators, then computes straight per-sample velocity as `delta * trunc(0x4000 / duration)`. Its nonzero-curve branch constructs two control points near one-third and two-thirds of the segment and delegates to `0x94BB80`; continuation initializer `0x94C620` can continue from current fixed-point velocity or start another curved segment. The demo now generates visible samples with this recurrence and the extracted curve branch; duration and normalized-to-native coordinate scale remain prototype inputs.
- `0x94E980` derives its curve scalar from target planar distance and flight-context `+0x140`. The 17-dword copy in `0x903840` maps source match `+0x184` to that flight field. The scalar is zero if the input is zero or distance is below `80` (`0x50`); otherwise the base is `(distance * input) / match[+0xA0DA8]`, ramped by `(distance-80)/170` for distances below `250`, and used at full value from `250` onward. Initializer `0x9598D0` writes `133` to match `+0xA0DA8`.
- Selector `0x9234A0` writes source match `+0x184` on verified branches: for action contexts 106/114 it selects a sign by comparing opaque player fields `+0xC4C` and `+0xC50`, with magnitude `floor(Random(player[+0xBD0]+2)/4)`; for action 123 it uses `RandomRange(-2,2)` (`-2..1`); another observed delivery branch explicitly writes zero. The offsets and upstream branch gates are not semantically mapped. `0x94C500` constructs the signed curve using a perpendicular offset from the start/end vector; `0x94BB80` converts the controls into cubic finite-difference coefficients in Q14, and `0x94C7B0` advances position, velocity, and acceleration by one sample. The demo now uses this recovered curve math when its prototype cross gate selects a cross; the cross gate and opaque-field proxy for the input remain inferred. Height, spin, collision, and bounce remain incomplete.
- Shots use a second curve-input slot. For the default shot action `300`, one selector path in `0x9234A0` initializes match `+0x1C0` with `RandomRange(-2,2)` (`-2..1`); a later gate can replace it with `(Random(player[+0xBD0]+2) * 11) / 30` when `Random(10) <= 0x8E9890()` and match field `+0x6D8` is below a global floating-point value. The player field and global threshold meanings remain unknown. In `0x92DF20`, the shot-state family passes match `+0x1C0` directly as the curve argument to `0x94E980`. Curled-effort action `316` starts from `[player+0xBD0]/3+5`; its follow-up can randomize that value using opaque fields `+0xC4C/+0xC50`, then applies a sign gate at context `+0x1C5`. Its final curve value is capped at ±12, while non-316 shots can be narrowed to ±2 in a separate condition. The demo samples the observed base action-300 input branch; the overwrite gate and the other shot-type formulas are still unresolved.
- Each sample is a 16-byte record. `0x94E980` copies four dwords from an input record into the sample array; if it takes the fallback path, it writes the current three values and zeroes the fourth dword. The first three are reused as the trajectory's three position components; the fourth field's meaning is unresolved. The builder also calls helper `0x9748C0` with bound `10000`, optionally passes that result to a context callback, and stores it at `+0x3F08`; the draw's effect on path construction has not been traced.
- The sampling helper `0x94CBB0` computes an integer progress percentage from two time arguments and a duration: `(timeB - timeA) * 100 / duration`. It then selects and interpolates among stored samples using integer multiply/divide operations and Euclidean-distance checks through `0x8C65E0`; a requested record index reaching `1000` takes an error/assert path. In a verified branch, the first two dwords of 16-byte records are interpolated using the time difference between records, while heading helpers `0x8C3810/0x8C3850` contribute fixed-point directional increments in another branch. Some intermediate terms are shifted by `14` bits, confirming a `2^14` fixed-point component. Mode flags and trajectory/context fields gate these branches, and their physical meanings remain unresolved, so this is not enough to claim a particular gravity or height model.
- `0x8C3810` and `0x8C3850` take a signed 16-bit heading and a magnitude, fetch separate components from heading/speed tables, and scale the table result when magnitude is at least `100`. `0x94CBB0` passes the trajectory heading at context `+0x5C` and a computed scalar to both helpers, then adds their results into two output coordinates. This confirms direction-vector motion in the sampled path; how that displacement relates to the third position component and the fourth record dword remains unknown.
- The trajectory sampler `0x94CBB0` computes integer progress `(endTime-startTime)*100/duration`, accumulates x/y from the 14-bit fixed-point state, and writes x, y, height, and an auxiliary dword into 16-byte records. It also checks pitch edges and the goal mouth: the observed goal-line corridor is centered on context `+0x28` with `±0x28` bounds (plus a one-unit crossing tolerance), while height gates include `0x1F` and net/back-wall limits. Goal/post/crossbar paths set context flags at `+0x3EF0/+0x3EFC/+0x3F00`, store a reflected heading at `+0x3F04`, and alter the sample step and velocity before continuing. These constants and state changes are confirmed; their field names, units, and complete collision/bounce response remain unresolved.
- `0x94C230` scans the recorded time values at `+0x3ED4` and returns the first one that is not earlier than the current match counter at `[match + 0xB0]`; if no stored sample qualifies, it returns the current counter. This links the trajectory sample list to the live match timeline, although the duration unit and cadence are still unknown.

The native engine therefore keeps a sampled trajectory timeline that off-ball decision code can query. The prototype's straight pass/shot path and its animation duration remain illustrative approximations.

## Recovered action labels

The name resolver at `0x8F5BF0` maps action IDs to embedded `ME_*` labels through jump tables and compact byte remaps. The reproducible extraction in [`action-state-name-map.csv`](action-state-name-map.csv) contains 210 named ID/label pairs; [`extract_action_names.py`](extract_action_names.py) regenerates it from the matching executable. The resolver's fallback text is `UNKNOWN ACTION`. An absent ID in the CSV therefore means “no named label recovered from this resolver,” not proof that the number can never occur internally.

The map now gives exact examples across the engine: passes and clearances (`100`, `102–124`), on-ball states (`200–214`), shot types (`300–316`), player movement/marking/interception (`400+` selected IDs), contests and ball control (`600–709` selected IDs), goalkeeper actions (`800–809` and `1000+`), tackling/fouls (`900+` selected IDs), and set-piece positioning (`1100+` selected IDs). IDs are sparse; do not treat the displayed spans as continuous enums. These are formatter labels, not evidence that each state is reachable in every match situation.

## Geometry helpers

- `0x8BC550` derives a bearing from an object's x/y at `+0x48/+0x4C` toward a target. If both coordinates match, it returns the object's heading at `+0x50`; otherwise it quantizes the deltas and looks up a heading in a table. This is the direction helper used in the run selector, not a distance result.
- `0x8C7610` computes the shortest circular difference between two 16-bit headings: absolute difference, folded around `360`, yielding a value up to `180`. Its callers compare against values such as `40` (`0x28`), confirming degree-like heading units.
- The late target-geometry phase of selector `0x9234A0` treats its candidate headings as 360-unit angles. In the branch around `0x92D09E–0x92D2CB`, each candidate is constrained to a window of `reference ± 25`, with wrap handling at 0/360; one path also applies a bounded random adjustment whose bounds depend on local values and match/player flags. The angle is then normalized back into the 0–359 range. On the vector-generation path, `0x8C3810/0x8C3850` convert the heading(s) and magnitude from context `+0x1B0` into components, and the selector adds pitch-origin fields `+0x6D0/+0x6D4` to write target coordinates at `+0x1A4/+0x1A8`. If two heading candidates differ, it averages their component offsets; if they match, it uses one vector. A branch with match field `+0x6 >= 202` and a separate local gate bypasses this conversion and copies precomputed coordinates. These are confirmed geometry operations; the internal field names, units, and tactical reason for choosing this branch remain unknown.
- `0x8C65E0` subtracts two coordinate pairs and calls `0x8C64D0`, which computes an integer square root of `dx² + dy²`. This confirms Euclidean-distance arithmetic, but not what one coordinate unit means in metres. A separate object-distance wrapper has an optional mode that remains unmapped.
- The extracted support files also include `direction_table.mdt` and `speed_direction_table.mdt`, each with 360 pairs of signed 32-bit direction components (their payload scales differ: `2^14` and `2^10`, respectively). They are separate from `distance_angle_table.mdt`; the low-magnitude branch of `0x8C3810/0x8C3850` is specifically backed by the latter. Their precise callers and role in the remaining movement/trajectory calculations are not yet proven.

## Randomness and conditional actions

- The random-state code at `0x9747A0` / `0x974850` uses a 624-word state, the `0x6C078965` seed recurrence, the `0x9908B0DF` twist constant, and the standard MT tempering masks. This is an MT19937-family generator. Wrapper `0x8BCA20` requests a bounded draw; the multiply-high scaling maps a positive bound `n` to an integer in `[0, n-1]`. A match-context callback can intercept the generated value, so the exact stream also depends on runtime setup.
- In one branch of the selector, `0x927B06` requests `Random(100)` and compares the result with a local threshold before selecting `208` (`ME_TAKE_A_DIVE`). This confirms a percentage-sized random gate in that branch, but the threshold's meaning and the other gates around it are not decoded.
- The demo now uses an MT19937 implementation and the same bounded-integer scaling as its random source. Its seed, random-call order, thresholds, and outcomes remain prototype choices; this does not reproduce the game's match sequence.
