# Championship Manager 03/04: static match-engine notes

## Public research cross-check (2026-11-26)

An internet search for prior CM 03/04 match-engine reverse engineering did **not** find a published source-level reconstruction. The useful public material found is design guidance rather than code: a contemporary community FAQ says attributes interact (its example combines vision and long shots for a chip) and that off-the-ball movement affects marking/shot opportunities, while pressure and bravery also alter contested outcomes. A later player guide claims physical attributes are weighted strongly, but this is anecdotal and is not a recovered formula. These statements are useful hypotheses to compare against native call graphs; they do not justify raising the reverse percentage.

The detailed public reverse-engineering article located is for **CM 01/02**, a different executable and engine version. Its exact grid dimensions, tick cadence, candidate weights, and numeric formulas must not be copied into this CM 03/04 reconstruction. Search results for current fan patches describe database/UI changes and faster 2D playback, not source-level match-engine recovery. The faster path remains to use the public guides to prioritize candidate attributes, then verify each dependency in this executable and in runtime traces.

### Team-relative attacking-end predicates (`0x8FA690`, `0x8FA720`)

The two helpers used in `0x9234A0` candidate adjustment are compact Y-band predicates. They compare `player+0x4C` with pitch height `player+0x78`, and choose orientation by whether `match+0x5EBC == player+0x6C`. `0x8FA690` returns 1 on the matching-team orientation for Y `<=299`, or on the opposite orientation for Y `> pitchHeight-300`; `0x8FA720` uses `<=449` and `> pitchHeight-450`. Otherwise they return 0. Thus these are side-relative end-band gates with 300- and 450-unit thresholds, not generic distance checks. Their callers use them to alter candidate scores; the identity of the reference team and score meaning remain unresolved. This resolves the exact polarity and field comparisons behind the previously noted 300/450 thresholds. Action-arbitration coverage rises from 44% to 45%; current six-area values `(45+68+54+48+32+43)/6 = 48.3%`, displayed as 48%.

One special arbitration branch applies additional caps when `[match+0x190] != 0`, `[match+0x194] == 0`, and its candidate-presence gate is not satisfied. Let `B = [match+0x194] * 50` (zero on this branch): it caps `local_84` at `B+25` and `local_74` at `B+50`. If `0x8FA720(player)` is true, player flag `[player+0xC6C] & 0x80` is clear, and `B+40+local_98 <= local_c8`, it also lowers `local_c8` to that bound. `local_98` starts as `Random([player+0xBEC]+2)`; in the position/side normalization branch it becomes at least `max(floor([player+0xBEC]/2),5)`, so the `local_c8` cap combines a bounded random draw with a field-derived lower bound. The selector later applies further pressure/contest adjustments, so these are intermediate candidate caps rather than final action weights. Match fields and `+0xBEC` remain unnamed. This adds a concrete context-specific relation between three arbitration candidates; action-arbitration coverage rises from 46% to 47%, with current mean `(47+68+54+48+32+43)/6 = 48.7%`, displayed as 49%.

The action-203 (`ME_HOLD_UP_BALL`) candidate is `local_84`. Its two multiplicative draws are now identified: both calls through `0x8E9930` return `Random([player+0xBB8]+2)`. In the nested state branch requiring `[player+0x8AF]==0`, `[player+0x9C1]==0`, selected match/player flags, and `[player+0x9C4]&1`, successful `0x8BB7D0` and `0x8FA660` gates lead to `local_84 = drawA*drawB - 200 + [player+0x9BC]` when `0x8BFA00` returns false (for this call, false means shortest heading-to-target difference is greater than 125°); `0x8BB7D0` is true exactly when `[player+0x882]&0x40` and `&0x700` are both nonzero, while `0x8FA660` compares player Y `+0x4C` against reference Y `+0x84` with orientation selected by side. The geometry call passes `x=[player+0x80]`, `y=0` or `[player+0x78]` from `0x8BB7A0(player)`, and threshold `250`; the helper returns false here when the shortest heading deviation from that target bearing exceeds 125°. Assembly shows the constants are already on the stack for `0x8BFA00`; the apparent `(0xFA,0)` arguments to `0x8BB7A0` in decompiler C are a calling-convention artifact. The score boost is also exact: if `Random([player+0xBF4]+2) != 0` and `[player+0xC6C]&0x800` is set, it becomes `max(local_84+500,500)`. When `local_b8` (the pressure value) is zero, a later path adds `[player+0x9BC]-100+Random(500)`. On a further branch, team instruction word `teamSubobject+0x890 == 0`, `Random(20) > 0x8F1A60(player)`, and `local_b8 < Random(max([player+0x9BC],20)/3)` can force 1000 if the candidate is still below 1000. `0x8F1A60` returns a control value from player mask `+0xC68` bits `0x40000/0x80000/0x100000/0x200000`, or team field `+0x884` when bit `0x800000` is set; if team byte `+0x570` is nonzero it returns 20. These recover the random bounds and several score gates, but not the meaning of `[player+0x9BC]`, `+0xBB8`, the full score. Action-arbitration coverage rises from 48% to 49%, and the current mean is `(49+68+54+48+32+43)/6 = 49.0%`.

The downstream case `0xCB` (203) in `0x92DF20` is also mapped in part. It runs its commentary/event selection only when `[player+0x882]&1` is clear and match byte `+0x41DA8` is set. Its first event candidates are `0x215A`, `0x215B`, `0x215C` for three combinations of `0x8C3360/0x8E9730/0x8F7310`, `0x8F72D0/0x8FA820`, and the 450-unit end-band helper `0x8FA720`; it additionally requires the player's Y to be within 100 units of the side reference `team+0x578`, and `0x8C7C50(event,160)` to return false. The `0x215D/0x215E/0x215F` family requires a role mask `+0x882&0x38`, a paired state/side gate, and Y separation greater than 150 from both teams' `+0x578` references before the same event check. A final group selects among `0x2160/0x2161/0x2162` or fallback event `8000` using `0x8C3380`, `0x8FA6C0`, `0x8FA560`, `0x8FA820`, and `0x8F7310`. The `events.cfg` lookup in `0x8E4420` subtracts base 8000 to index the event table, so these are now mapped to source labels: `0x215A–0x215C` = `EVENT_IN_LEFT/CENTRAL/RIGHT_DEFENCE`; `0x215D–0x215F` = `EVENT_IN_LEFT/CENTRAL/RIGHT_MIDFIELD`; `0x2160–0x2162` = `EVENT_IN_LEFT/CENTRAL/RIGHT_ATTACK`; fallback `8000` = `EVENT_WAIT` (“holds up the ball”). `0x2161` specifically reports distance to goal in yards. The mapping is recorded in `reverse/cm0304-event-map.csv`, and source `events.cfg` identity/hash is in the manifest. Regardless of which event path is taken, the dispatcher copies `[player+0x8C8]` to `+0x9BC`, snapshots ten dwords from `+0x8BC` to `+0x8E4`, and schedules the next update for `[match+0xB0]+1` with `+0x9CC=1`. Most helper semantics and the tactical condition for each region remain unresolved. Action-arbitration coverage rises from 50% to 51%, producing mean `(51+68+54+48+32+43)/6 = 49.3%`, displayed as 49%.

`0x8C7C50(eventId,160)` is an event-repeat gate. When the event subsystem is enabled at `+0x41DA8`, it compares current match tick `[context+0xB0] - 160` against a per-event dword at `[context+0x38B70 + eventId*4]`; if the event timestamp is newer than that 160-tick cutoff, it returns true and the caller suppresses the message. Thus 160 is a match-tick lookback interval for deduplicating region commentary, not a player-decision score or spatial distance. This exact gate raises action/event handling coverage from 51% to 52%; six-area mean is `(52+68+54+48+32+43)/6 = 49.5%`, displayed as 50%.

### Attacking throw-in target modes (`0x919F80`, actions 1700–1706)

The selected action family is named by the executable as `ME_ATT_THROW_LEFT_DEFAULT`, `...COME_SHORT`, `...LURK_OUTSIDE_AREA`, `...NEAR_POST`, `...STAY_BACK`, `...FORWARD`, and `...MARK_PLAYER`. In the target-construction branch, `player+0xB10` is a one-based rank, not an instruction ID: `0x8B2BB0` copies selected profile metadata at `+0x44`, and roster pass `0x9603A0` assigns sequential ranks to players whose corresponding metadata word has bit `0x40` set. It first sorts the candidate roster with comparator body `0x95FCC0`: the comparison key starts at `-[player+0xBB0]`, is adjusted by branch-dependent role/state gates and native predicates (observed adjustments `+50`, `+25`, `+10`, or `-20`), and ties are broken by player field `+0xC`. `qsort` receives the comparator in descending-key order; the sorted index becomes the rank at `+0xB10`. Exact semantic names for the field and predicates remain unknown. The movement routine enters this branch when the resulting player mask `+0xC74 & 0x40` is set. Ranks 1, 2, and 3 choose base headings `0xE6`, `0x14A`, and `0x104` degrees respectively, mirrored by the player's side byte `+0x5B`; they draw distances from `[120,150)`, `[150,200)`, and `[120,180)`, then jitter heading by `[-10,10)` degrees. The resulting vector is offset from match reference `[match+0x6E0/+0x6E4]`, and Y is clamped to `[40,pitchHeight-40]`. If the active ball-player context exists, its action/tick relation changes the distance and can jitter the base heading; a late-match condition also enforces a minimum distance-like value of 60. If the generated target is more than 200 native units from the thrower, the routine sets action 411 (`ME_MOVE_TO_RECEIVE_THROW`) and movement mode `0x10`; otherwise it falls through to the surrounding throw-action setup. Other ranks/branches use profile target generation `0x905710` or a defender/keeper-relative construction. The meaning of the `0x40` profile group, `+0xBB0` score, rank ordering policy, target units, recipient choice, and downstream throw/pass result remain unresolved. This evidence raises the pass/shot/set-piece checklist area from 52% to 53%; keeping other categories at 42/67/48/32/43 gives a six-area mean of 47.5%, displayed as 48%.

The action dispatcher `0x92DF20` groups all seven IDs `1700..1706` into the same movement-path maintenance case. It sets the next deadline to `matchTick + [match+0xC8]` and marks the deadline active at player `+0x9CC`. It preserves the existing path only when Manhattan target-to-player distance is below 20 and current action `+0x8F4` still matches queued action `+0x8CC`; otherwise it calls `0x8EB4C0(targetX,targetY,estimate,mode)` to rebuild the movement path. Thus the seven modes share a verified refresh/continuation contract even though their target policies differ. This raises movement/off-ball coverage from 67% to 68%; the updated six-area mean is `(42+68+53+48+32+43)/6 = 47.7%`, displayed as 48%.

The follow-up action 411 (`ME_MOVE_TO_RECEIVE_THROW`) has its own dispatch path in `0x92DF20`. Its deadline is `matchTick + [match+0xC8]` when player `+0xAF8` is zero, otherwise `matchTick + 8`; it sets the active deadline byte `+0x9CC`. A Manhattan distance below 20 suppresses path rebuilding only when player mask `+0x882` bit 0 is clear or byte `+0xAA7` is nonzero. Otherwise it calls the same `0x8EB4C0` path builder and snapshots ten dwords from `+0x8BC` to `+0x8E4`; it also stamps the current match tick to `[match+0xE0]`. A separate gated branch stores the player pointer in team field `+0x59C`. The gate semantics and the special role of the two deadline lengths remain unresolved. This increases pass/shot/set-piece coverage from 53% to 54%; with other categories at 42/68/48/32/44 the mean is 48.0%.

## Observed action-state flow

- The selection routine beginning at `0x9234A0` writes an action identifier into `[object + 0x8CC]`. An action-processing routine begins near `0x92DF20`.
- In one on-ball arbitration block of `0x9234A0`, the selector adjusts five local candidate values (`local_74`, `local_c8`, `local_84`, `local_a8`, `local_a4`) with `0x8BCA50(-5, 5)` when each is greater than `5`; that helper returns `min + Random(max-min)`, so the adjustment is `-5..4`. It selects `202` (`ME_TURN_ON_BALL`) when `local_74` is positive and below the other four values (the last comparison is `local_a4 <= local_74`). If that branch does not win, it selects `203` (`ME_HOLD_UP_BALL`) when adjusted `local_84` is positive and below `local_c8`, `local_a8`, and `local_a4` (again `local_a4 <= local_84`). Both branches set the movement target to the player's current coordinates; `202` uses movement flags selected from geometry/state gates (`0x80`, `0x100`, `0x80000`, or `0x200000`), while `203` uses `0x10`. A `203` choice is changed to `212` (`ME_GK_DROP_BALL_FOR_DISTRIBUTION`) on a separate goalkeeper flag/state gate, which also clears `[player + 0x8AD]`. This verifies part of the arbitration and tie-jitter behavior, but the candidate values' tactical meanings and their input weights are still unknown.
- In the run-with-ball path, the code compares the absolute x and y target deltas with `10`. It selects action `201` when both are strictly below `10`; otherwise it selects `200`. The source field units have not been mapped to metres.
- Other constant writes in the same selector confirm branches for `204` (`ME_WAIT_TO_FIND_SET_PIECE_ACTION`), `208` (`ME_TAKE_A_DIVE`), `212` (`ME_GK_DROP_BALL_FOR_DISTRIBUTION`), `213` (`ME_ATTEMPT_TO_ROUND_KEEPER`), and `1000` (`ME_GK_USE_SIX_SECONDS`). The meaning of mask `0x780` and the deadline's units remain unknown. The `208` branch is now mapped further: it requires player flag bit `1` at `+0x9C4`, a false result from `0x5AB230`, `[player + 0x988] < [match + 0xB0]`, then three separate `Random(5000)` draws greater than candidates `local_a8`, `local_c8`, and `local_a4`. - A fresh full decompilation of `0x8FE890` resolves more of that score. The teammate-list ordering/field `+0x64`, match offsets, and return labels' tactical meanings remain unknown, so this is recovered arithmetic and branch behavior, not a named football rule.

### Trajectory origin and bounce response (batched helper follow-up)

The initializer `0x94C130` has two distinct origin paths. With an explicit source object it copies that object's coordinates at `+0x48/+0x4C`. Without one, it requires the active ball-player pointer `[match+0x423F8]`, samples that player's position at the current match tick with `0x8BBAC0`, reads heading at player `+0x50`, and passes the point through `0x8C6DC0` before storing it as the trajectory origin. A missing active ball-player pointer logs an error and returns without initializing.

`0x8C6DC0` adds an angle-table offset and then clamps the result against that player's pitch bounds (`+0x7C/+0x78`). In its mode-1 call from `0x94C130`, it takes the table entry indexed by `heading * 5` (60-byte record stride); the other mode selects one of five offset tiers from `clamp(5 - [player+0x9BC]/50, 0, 4)` and scales the offset by `max(14 - [match+0x6D8],0)/20`. If the adjusted point crosses a boundary, a margin is derived from `5 - [player+0x8B0]/([player+0xBD0]+1)`, clamped to the pitch edge, and `0x8FA9D0` is called when player byte `+0x9BB` is zero. These are exact coordinate and field dependencies; the table's football meaning, the fields' names, and why the caller selects either mode remain unknown.

### Shot-selection threshold helper (`0x8EDE60`)

The `local_b4` threshold used by the shot selector is partly produced by `0x8EDE60(player, distance, randomize)`. ### Angle lookup resource and exact heading path (`0x8CB750`, `0x8BC550`)

Initializer `0x8CB750` opens `angle_lookup_table` from the game's `tables` directory and reads 300 rows × 400 signed 16-bit values into `0xDAF2E0`. ### Sampled-path candidate scorer and fallback chain (`0x904840`)

A fresh full-function Ghidra decompilation sharpens the earlier flag-by-flag summary. The helper scans trajectory records of 16 bytes from the current match tick (or the next tick when `flags&0x20` is clear) through a context-derived upper bound, starting with best score 2000. It returns the selected record's absolute tick and writes its x, y, and auxiliary word; the auxiliary word is not the score. With the ordinary distance arm, the base is integer Euclidean distance from the player to the record. Flag `0x4` adds absolute x separation from player reference `+0x80`. Flag `0x400` changes the score by a nonnegative time-window term based on trajectory context `+0x0C` and the candidate tick. The score update is strict (`candidate < best`), so equal scores preserve the earlier selected point.

When `flags&0x2` is active, reachability is evaluated through `0x8BCF50` at the candidate time. Its mode-0/mode-1 results select separate branches: a failed mode-0 gate adds 200; the other paths compare arrival distances/times and can rescale the current score using `(candidateTick-startTick)/2` with a floor of one. The same flag also enables an initial random pre-gate: `R3 < ((signed(player+0x7BE)/2+10) * R2 * R1)`, where `R1=Random(player+0xB8C+2)`, `R2=Random(player+0xB90+5)`, and `R3=Random(100)`. A successful pre-gate produces a randomized target through `0x8BC3C0`; those candidates can receive an additional distance-to-random-target comparison. This confirms both the random bounds and how they intersect the discrete path scan, but the source fields and helper outputs are still not named tactically.

Further eligibility is flag- and match-phase-dependent: `0x200` invokes `0x901C70` at the candidate coordinates; `0x100` changes the distance reference and applies side-oriented x/y windows (including strict ±220 x bands) and time cutoffs; `0x800` applies movement-time gates derived from `(player+0xBB0+2)/3+19`; `0x8` rejects high-score late samples except designated-player cases and applies a team-instruction side/distance predicate. `0x10` and `0x1000` can stop scanning after a sufficiently good/first reach candidate. The exact branch predicates are now visible in the decompilation, but the flag names, several temporal fields, random state and desired action remain unresolved.

When no candidate is selected, the routine does not have one universal result. Depending on flags and match phase, it can return `-1`, use the current ball position/time, choose a designated player's arrival sample (`match+0x1EC` or `+0x423E0`), choose a queued trajectory time (`+0xD0`), or fall back to a clamped endpoint from trajectory context `+0x3C/+0x40/+0x44`. The designated-arrival branches clamp negative sample coordinates to zero and coordinates above the pitch dimensions to the boundary. This completes the sampled selector's main score skeleton and fallback inventory, but not all predicates, contextual field meanings, runtime parity or its integration into movement actions. Off-ball/path evaluation coverage rises from 68% to 70%; six-area mean `(58+70+54+48+32+43)/6 = 50.8%`, displayed as 51%.

### Exact sampled-point reach gate (`0x8BCF50`)

Instruction-level argument mapping resolves the helper as `(player, targetX, targetY, sampleTick, mode)`; it returns a strict comparison, not a distance. It forms `baseDistance` from `target - playerPosition - headingVector`, where `headingVector` is the first signed `(x,y)` pair from the already identified `ball_at_feet_offsets.mdt` table at `0xDA9E78`, indexed by player heading `+0x50` with a 60-byte (five-pair) stride. The cardinal entries are heading 0 `(0,15)`, 90 `(15,0)`, 180 `(0,-15)`, and 270 `(-15,0)`, so `D` compares the candidate with player position offset by the native ball-at-feet point for the current heading. It obtains `targetBearing = 0x8BC550(player,targetX,targetY)` and `sideBearing = 0x8BC550(player,[player+0x80], [player+0x5B] ? [player+0x78] : 0)`. Each `0x8C7610(a,b)` is now exact: `d=abs(signed16(a)-signed16(b))`, then if signed16(d)>180 return `360-signed16(d)`, otherwise return d. Thus the two terms are unsigned shortest-arc heading differences `a1=angle(playerHeading,targetBearing)` and `a2=angle(targetBearing,sideBearing)`, each 0..180 for normal heading inputs. Let `speed=min(signed([player+0x60]),40)`, `dt=max(sampleTick-[match+0xB0],1)`, and `D=integerDistance(target, playerPosition+headingVector)`. The final integer metric is `M = (D + floor(15*(a1+a2)/speed)) / dt` under native signed integer division; mode nonzero accepts only `M<10`, mode zero accepts only `M<30`. The instructions cap speed only above at 40; a positive field value is an invariant assumed by this formula, since zero/negative values are not clamped before division. The native field at `+0x60` acts as the divisor, but its attribute label/unit and the offsets' coordinate scale remain unknown.

This is the core geometric/time-to-arrival gate used by `0x904840`; it explains why the helper can reject a nearby point if its arrival window is too short or the two bearing turns are expensive, and why the caller's two modes produce different strict thresholds. This derivation is from the function's x86 instructions and call argument cleanup (`RET 0x10`), not a fit to the demo. The branch-specific caller weighting and whole action choice are still not fully reversed. Off-ball/path-evaluation coverage rises from 70% to 74%; six-area mean `(58+74+54+48+32+43)/6 = 51.5%`, displayed as 52%.
