# Championship Manager 03/04: static match-engine notes

## Scope and target

These are partial static observations from the user-provided Windows release. The inspected executable is PE32 x86, version 4.1.0.0, SHA-256 `f5963ebd6c9df918b9e630402a3bed6a64357f7ff62b9a6d2a6b5d5234bd9b7a`. Addresses below are virtual addresses from the executable image. They have not been validated against other releases.

This is not a 100% reconstruction. Decision weights, most attribute effects, several helper predicates, and the full ball/shot model remain unresolved. The HTML demo deliberately labels inferred behavior.

## Observed action-state flow

- The selection routine beginning at `0x9234A0` writes an action identifier into `[object + 0x8CC]`. An action-processing routine begins near `0x92DF20`.
- In the run-with-ball path, the code compares the absolute x and y target deltas with `10`. It selects action `201` when both are strictly below `10`; otherwise it selects `200`. The source field units have not been mapped to metres.
- Other constant writes in the same selector confirm branches for `204` (`ME_WAIT_TO_FIND_SET_PIECE_ACTION`), `208` (`ME_TAKE_A_DIVE`), `212` (`ME_GK_DROP_BALL_FOR_DISTRIBUTION`), `213` (`ME_ATTEMPT_TO_ROUND_KEEPER`), and `1000` (`ME_GK_USE_SIX_SECONDS`). Their exact predicates are still being mapped.
- The run selector also calls shared helper `0x8FE890` (26 direct call sites in the executable). It scans candidate objects under a match context and uses geometry helpers. Its observed return paths produce byte values `0`, `1`, and `2`; the two run-selector branches use opposite zero/nonzero tests before choosing action `205`. Treat it as a tri-state helper whose exact meaning depends on the caller, not a global boolean “success” flag.
- The action processor at `0x92DF20` calls `0x8EB4E0` with the current action ID. That helper special-cases IDs `501–510`, writes one of ten associated constants to an output slot, and returns true; other IDs write `100` and return false. These action IDs are named as foul/violent-play events in the resolver, but the meaning of the secondary constants has not been identified.
- At the start of this processor, the current match counter at `[match + 0xB0]` is copied to `[player + 0x8D4]`, then the action ID at `[player + 0x8CC]` is passed to the special-case helper. One bounded random draw uses a bound derived as `[player + 0xB90] + 5`. If `[player + 0x64]` is at least `50` and the action is outside the helper's `501–510` set, this path branches out before the later action work. The meanings of these player fields, the draw's consumer, and the `50` threshold units are not yet established.
- The observed shot path is `0x93181B → 0x94C0D0 → 0x94E980 → 0x94CBB0`. `0x94E980` repeatedly asks `0x94CBB0` for trajectory samples, increments a sample count at `+0x3EE8`, and stores values from `+0x3ED8`. A comparison against `999` bounds the loop to about 1000 samples (indices 0–999). A coefficient helper uses `0x4000` (16384) as a fixed-point scale; the coordinate units and complete trajectory equations are still unresolved.
- The normal-pass action `100` routes through a branch around `0x92EF36` and calls `0x903840`. That routine copies a 17-word context record from offset `+0x15C` to `+0x118` before related match-context updates.
- The selector also constructs restart/delivery contexts. At `0x929B58` it writes action `108`; a nearby branch writes `106` or `114` to context `+0x15C` according to bit `0x40` in player flags at `+0x9C4`. The embedded labels identify these as halfway clearance, cross into area, and corner. This establishes the state values and a flag-controlled split, but not the full trigger meaning.
- Another branch writes `118` (`ME_THROW_DOWN_LINE`) to the context at `0x929E67`. Before that write, it derives two target components through `0x8BC320`, `0x8BC550`, and the vector helpers `0x8C3810/0x8C3850`; it also fills adjacent context fields and then copies the selected ID into the player's `+0x8CC` action field. Their meanings and units remain unresolved.
- A separate construction branch writes `116` (`ME_GOAL_KICK`) at `0x92A25C`. It forms one target component by adding the result of a bounded helper call supplied with `-200` and `200` to a stored coordinate, copies another coordinate directly, fills additional context fields, then reaches the common action write at `0x92D5F5`. The supplied bounds are observed constants; their interpretation and the target record's field semantics have not been dynamically checked.

## Off-ball movement and interception

The player decision block around `0x93AE98–0x93B17A` contains live off-ball movement branches. It writes the chosen action at `[player + 0x8CC]`, movement target coordinates at `+0x8BC/+0x8C0`, and then joins the shared action path at `0x9468D0`.

- One branch chooses `400` (`ME_MOVE_TO_BALL`). It first checks the match-context pointer at `+0x423F8`, a predicate at `0x8FA560`, team identity, and the values at player `+0x9B8` and match time `+0x64`. When that path is reached before time `20`, it asks `0x911840` for a state and stores the return value; `601` is explicitly treated as a special case. If the branch continues, `0x8C6080` is called with the player and match coordinates, the resulting index selects entries from global tables at `0xDA9E78/0xDA9E7C`, and the target is formed from the match coordinates minus those entries. It sets movement mode `4`. The table contents' semantic names and coordinate scale are unresolved.
- The interception branch calls `0x904840` with flags `0x100A` and output slots for two target coordinates plus an auxiliary value. The helper obtains the trajectory object through `[player + 0x68] + 0x68`, reads its sample base index at `+0x4` and count at `+0x8`, then scans 16-byte records beginning at `+0x58`. For each candidate it uses the first two dwords as target coordinates and calls `0x8C65E0` for Euclidean-distance checks; flag-dependent branches also filter the third and fourth dwords against small constants. The helper returns a signed selector value (`-1` is the no-candidate sentinel on this path) and writes the selected coordinates plus an auxiliary output. That output is not the same field on every return path, and its meaning remains unresolved. The selector's units are also unknown. The caller stores it at `[player + 0x8D0]`, computes another estimate through `0x8BC3C0`/`0x8C0420`, subtracts `2` from that estimate when `0x8EE780` is true, and rejects the candidate if the adjusted estimate exceeds the helper's result. If match-context `+0x1EC` is not `-1`, the estimate must also be no greater than that field. The meanings and units of both compared values are not yet mapped.
- One input to that comparison is now traced more precisely. `0x8BC3C0` computes `3 * (50 - [player + 0x30]) + 3/2 * ([player + 0x348] - penalty)`, where `penalty` is zero when `[player + 0xC0] <= 1600` and otherwise `(field - 1600) / 20` capped at `10`. If `[match + 0x6] >= 0xD7`, the result is capped at `30`. The caller passes this value with the candidate x/y coordinates and option `4` to `0x8C0420`, a wrapper around `0x8BD030`, before comparing the returned estimate with the trajectory selector. These player fields, the option, and the units of the result are still unnamed.
- Once a candidate passes those gates, an auxiliary output below `15` chooses `414` (`ME_MOVE_TO_INTERCEPT_BALL`); otherwise it chooses `452` (`ME_MOVE_TO_INTERCEPT_HIGH_BALL`). The target is adjusted using bearing helper `0x8BC550` and the same global side tables, then movement mode `4` is set. The planner also compares the third sample dword with thresholds including `10`, `15`, and `20`, and in one flag-conditioned path rejects records whose fourth dword is at most `15`. The `<15` split and these sample fields are consistent with a height/elevation test, but their exact source-field mapping and units are not proven.
- A separate branch uses predicate `0x8FA660` and helper `0x8C0990`; when its returned value is greater than `-40`, it writes an adjusted target and selects `403` (`ME_MOVE_ONSIDE`) with movement mode `0x10`. This is consistent with the action's embedded label, but the helper result, threshold units, and complete trigger conditions remain unresolved.
- The long movement-maintenance routine beginning at `0x9468F0` revisits states `400/401` and `414/415/452`, compares stored candidate values at `+0x8D0` with match time/counter fields, and can recompute targets through `0x94BF40`, `0x8BBAC0`, and `0x904840`. The same `0x904840` helper is called there with several other flag masks (`0x2065`, `0x20AA`, `0x2025`), showing that target prediction is shared by multiple movement paths. Exact flag meanings and the full update cadence remain unresolved.
- The player-position refresh path is distinct from the ball's 16-byte trajectory samples. `0x919EF0` sets a per-player update deadline at `[match + 0xB0] + duration` in `[player + 0x9C8]`, clears `[player + 0x9CC]`, and calls `0x918460`; when argument bit `1` is set, it also calls `0x8BBA10` and `0x904640`. That helper calls `0x8BBAC0` with the current match counter and output pointers for player fields `+0x48/+0x4C/+0x50/+0x54` and `+0xB8`. `0x8BBAC0` reads a separate 28-byte-stride motion record array at `[entity + 0x14]`: before endpoint time `[entity + 0x34]`, it selects a record using `max(requestedTime - [entity + 0x24], 0)`; at/after that time it outputs endpoint coordinates from `+0x38/+0x3C`. It compares selected x/y with the current x/y and returns a changed flag. This helper selects timed samples; any interpolation between them must occur elsewhere and has not yet been found.
- When one of those movement states reaches a later timing/context gate, `0x9468F0` clears the movement target, sets mode `0x10`, calls `0x913BB0`, and copies its return value into the player's primary action at `+0x8CC`. The resolver samples the trajectory around match counter minus `2` through `0x94BF40`, applies a `0x8BFA00` proximity predicate with argument `250`, and checks the player's current substate and several match-time/context fields. Before resolving an outcome it combines a bounded draw using `[player + 0x344]`, an integer `3/2` scaling of the signed byte `[player + 0x7BC]`, and a bounded draw using `[player + 0xBE4] + 2`; it multiplies that sum by `[match + 0xA0F2C]` and divides by `100`. Later branches compare against `[match + 0x6D8]` and use further bounded draws from player fields `+0xBB0` and `+0xBE0`. The exact meanings of these inputs and the resulting score are unknown. Observed return values include `600` (`ME_NOT_SAVED`) and goalkeeper outcomes `800–806` (`ME_SAVE_HELD` through `ME_GOALIE_SCATTER_BALL`). A branch on trajectory byte `+0x59` selects among numeric bases `100`, `200`, `300`, `400`, and `800` for later bounded-random threshold calculations; the byte's type names and complete outcome weights are not recovered. This is evidence for a separate ball-arrival/result resolver after interception movement, not a complete save or contact formula.
- The action processor contains a separate set-piece preparation transition: when `[player + 0x8F4]` is `450` (`ME_STEP_BACK_TO_TAKE_SET_PIECE`), the action at `+0x8CC` is not `204`, a bit in `[player + 0x9C4] & 0x6C0` is set, and `[match + 0xB0] >= [player + 0x34]`, it computes a new position from the match's team reference coordinates and the same `0xDA9E78/0xDA9E7C` tables. It then changes `+0x8F4` to `451` (`ME_STEP_UP_TO_TAKE_SET_PIECE`) and calls movement/update helpers. The bit meanings, clock units, and exact semantics of the adjacent player fields are unresolved.

These branches establish that movement decisions use a predicted ball-path record set and explicit competing reach/index checks. They do not expose the full scoring formula, all action transitions, or a direct mapping from simulation units to field coordinates.

## Ball trajectory state

- The action dispatcher routes `100` (`ME_NORMAL_PASS`) through `0x8BC0D0` and then `0x903840`. That worker calls the trajectory initializer `0x94C0D0` and builder `0x94E980`, supplying values from the match's outgoing-ball context around `+0x118..+0x140`. After building the path it updates the match's active-player pointer at `+0x42408`, toggles the involved players' `+0x8A2` ownership byte, clears the interception-candidate pointer at `+0x423F8`, and snapshots current ball coordinates into match fields `+0x12C..+0x134`. This connects a selected pass action to the sampled ball-flight path and ownership bookkeeping. The precise context-slot meanings, pass success calculation, and resulting path parameters are still unresolved.
- `0x94C0D0` initializes a trajectory object from three supplied coordinate values, resets trajectory counters/flags, and copies the match counter at `[match + 0xB0]` into its initial time fields. When there is no explicit source object, a neighboring initializer (`0x94C130`) asks `0x8BBAC0` for a current position based on the match's active ball object before initializing the trajectory.
- `0x94E980` builds the time/position samples. It stores position records at 16-byte strides beginning at object `+0x58`, tracks sample metadata around `+0x3ED4/+0x3ED8`, and increments a count at `+0x3EE8`. A loop bounds its sample index to `0..999`; `0x94CBB0` also guards against an index reaching `1000`.
- Each sample is a 16-byte record. `0x94E980` copies four dwords from an input record into the sample array; if it takes the fallback path, it writes the current three values and zeroes the fourth dword. The first three are reused as the trajectory's three position components; the fourth field's meaning is unresolved. The builder also calls helper `0x9748C0` with bound `10000`, optionally passes that result to a context callback, and stores it at `+0x3F08`; the draw's effect on path construction has not been traced.
- The sampling helper `0x94CBB0` computes an integer progress percentage from two time arguments and a duration: `(timeB - timeA) * 100 / duration`. It then selects and interpolates among stored samples using integer multiply/divide operations and Euclidean-distance checks through `0x8C65E0`. Some intermediate terms are shifted by `14` bits, confirming a `2^14` fixed-point component, but the complete coordinate and velocity equations are not yet recovered. Additional branches compare trajectory components and floating-point values; their fields and physical meanings are still unmapped, so this is not enough to claim a particular gravity or height model.
- `0x8C3810` and `0x8C3850` take a signed 16-bit heading and a magnitude, fetch separate components from heading/speed tables, and scale the table result when magnitude is at least `100`. `0x94CBB0` passes the trajectory heading at context `+0x5C` and a computed scalar to both helpers, then adds their results into two output coordinates. This confirms direction-vector motion in the sampled path; how that displacement relates to the third position component and the fourth record dword remains unknown.
- `0x94C230` scans the recorded time values at `+0x3ED4` and returns the first one that is not earlier than the current match counter at `[match + 0xB0]`; if no stored sample qualifies, it returns the current counter. This links the trajectory sample list to the live match timeline, although the duration unit and cadence are still unknown.

The native engine therefore keeps a sampled trajectory timeline that off-ball decision code can query. The prototype's straight pass/shot path and its animation duration remain illustrative approximations.

## Recovered action labels

The name resolver at `0x8F5BF0` maps action IDs to embedded `ME_*` labels through jump tables and compact byte remaps. The reproducible extraction in [`action-state-name-map.csv`](action-state-name-map.csv) contains 210 named ID/label pairs; [`extract_action_names.py`](extract_action_names.py) regenerates it from the matching executable. The resolver's fallback text is `UNKNOWN ACTION`. An absent ID in the CSV therefore means “no named label recovered from this resolver,” not proof that the number can never occur internally.

The map now gives exact examples across the engine: passes and clearances (`100`, `102–124`), on-ball states (`200–214`), shot types (`300–316`), player movement/marking/interception (`400+` selected IDs), contests and ball control (`600–709` selected IDs), goalkeeper actions (`800–809` and `1000+`), tackling/fouls (`900+` selected IDs), and set-piece positioning (`1100+` selected IDs). IDs are sparse; do not treat the displayed spans as continuous enums. These are formatter labels, not evidence that each state is reachable in every match situation.

## Geometry helpers

- `0x8BC550` derives a bearing from an object's x/y at `+0x48/+0x4C` toward a target. If both coordinates match, it returns the object's heading at `+0x50`; otherwise it quantizes the deltas and looks up a heading in a table. This is the direction helper used in the run selector, not a distance result.
- `0x8C7610` computes the shortest circular difference between two 16-bit headings: absolute difference, folded around `360`, yielding a value up to `180`. Its callers compare against values such as `40` (`0x28`), confirming degree-like heading units.
- `0x8C65E0` subtracts two coordinate pairs and calls `0x8C64D0`, which computes an integer square root of `dx² + dy²`. This confirms Euclidean-distance arithmetic, but not what one coordinate unit means in metres. A separate object-distance wrapper has an optional mode that remains unmapped.

## Randomness and conditional actions

- The random-state code at `0x9747A0` / `0x974850` uses a 624-word state, the `0x6C078965` seed recurrence, the `0x9908B0DF` twist constant, and the standard MT tempering masks. This is an MT19937-family generator. Wrapper `0x8BCA20` requests a bounded draw; the multiply-high scaling maps a positive bound `n` to an integer in `[0, n-1]`. A match-context callback can intercept the generated value, so the exact stream also depends on runtime setup.
- In one branch of the selector, `0x927B06` requests `Random(100)` and compares the result with a local threshold before selecting `208` (`ME_TAKE_A_DIVE`). This confirms a percentage-sized random gate in that branch, but the threshold's meaning and the other gates around it are not decoded.
- The demo now uses an MT19937 implementation and the same bounded-integer scaling as its random source. Its seed, random-call order, thresholds, and outcomes remain prototype choices; this does not reproduce the game's match sequence.

## Tactical inputs

The game data includes team instructions for passing style, passing focus, tackling, closing down, mentality, offside trap, zonal marking, counter-attacking, and men behind the ball. Player instructions can override individual behaviors, including run-with-ball and hold-up behavior. The existence of an instruction is confirmed; its exact contribution to action scores is not.

## Demo boundary

Its defenders sample the prototype ball path to choose an earliest reachable point, but it does not execute the native interception planner. Receiver selection, player motion during ball flight, pressing targets, shot choice probabilities, restart handling, and outcomes remain independent prototype rules. The native `106/108/114/116/118` state construction above is documented but is not simulated by the prototype. The CSV documents the game's state labels; it does not make those prototype rules recovered engine behavior.
