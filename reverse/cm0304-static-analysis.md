# Championship Manager 03/04: static match-engine notes

## Scope and target

These are partial static observations from the user-provided Windows release. The inspected executable is PE32 x86, version 4.1.0.0, SHA-256 `f5963ebd6c9df918b9e630402a3bed6a64357f7ff62b9a6d2a6b5d5234bd9b7a`. Addresses below are virtual addresses from the executable image. They have not been validated against other releases.

This is not a 100% reconstruction. Decision weights, most attribute effects, several helper predicates, and the full ball/shot model remain unresolved. The HTML demo deliberately labels inferred behavior.

## Observed action-state flow

- The selection routine beginning at `0x9234A0` writes an action identifier into `[object + 0x8CC]`. An action-processing routine begins near `0x92DF20`.
- In one on-ball arbitration block of `0x9234A0`, the selector adjusts five local candidate values (`local_74`, `local_c8`, `local_84`, `local_a8`, `local_a4`) with `0x8BCA50(-5, 5)` when each is greater than `5`; that helper returns `min + Random(max-min)`, so the adjustment is `-5..4`. It selects `202` (`ME_TURN_ON_BALL`) when `local_74` is positive and below the other four values (the last comparison is `local_a4 <= local_74`). If that branch does not win, it selects `203` (`ME_HOLD_UP_BALL`) when adjusted `local_84` is positive and below `local_c8`, `local_a8`, and `local_a4` (again `local_a4 <= local_84`). Both branches set the movement target to the player's current coordinates; `202` uses movement flags selected from geometry/state gates (`0x80`, `0x100`, `0x80000`, or `0x200000`), while `203` uses `0x10`. A `203` choice is changed to `212` (`ME_GK_DROP_BALL_FOR_DISTRIBUTION`) on a separate goalkeeper flag/state gate, which also clears `[player + 0x8AD]`. This verifies part of the arbitration and tie-jitter behavior, but the candidate values' tactical meanings and their input weights are still unknown.
- In the run-with-ball path, the code compares the absolute x and y target deltas with `10`. It selects action `201` when both are strictly below `10`; otherwise it selects `200`. The source field units have not been mapped to metres.
- Other constant writes in the same selector confirm branches for `204` (`ME_WAIT_TO_FIND_SET_PIECE_ACTION`), `208` (`ME_TAKE_A_DIVE`), `212` (`ME_GK_DROP_BALL_FOR_DISTRIBUTION`), `213` (`ME_ATTEMPT_TO_ROUND_KEEPER`), and `1000` (`ME_GK_USE_SIX_SECONDS`). The meaning of mask `0x780` and the deadline's units remain unknown. The `208` branch is now mapped further: it requires player flag bit `1` at `+0x9C4`, a false result from `0x5AB230`, `[player + 0x988] < [match + 0xB0]`, then three separate `Random(5000)` draws greater than candidates `local_a8`, `local_c8`, and `local_a4`. Several compared fields and context helpers are still unnamed, so this recovers a gate structure and output state rather than the underlying attribute model.
- The `213` (`ME_ATTEMPT_TO_ROUND_KEEPER`) branch is reached when local candidate `local_c8` is positive and beats `local_a4` and `local_a8`, and the previously derived candidate target passes its `local_3d` gate. That target gate starts only when `[player + 0x9C1]` is set, `local_ba` is clear, and `local_b8 < 60`; it then compares a `Random(25000) / max(0x8E9890(),1)` value with a random bound derived from `([signed_byte(player+0x818)]^2 / 20) * [player+0xBD0] * [player+0x348]`, and requires `[local_60] < 20`. Targets with y below `20` or above `[player + 0x78]-20` are rejected. A further gate accepts when `[match + 0x6] < 218`, `local_78 == 0`, or the circular heading difference is at most `60 - distance/10`; otherwise it restores the prior candidate. A selected target is written to `+0x8BC/+0x8C0`, movement mode `0x410` is set, `(local_98 - 20) * 15 + [player + 0x9BC]` is stored in `+0x8C8`, and the `0x8BC3C0` estimate goes to `+0x8C4`. - The run selector also calls shared helper `0x8FE890` (26 direct call sites in the executable). It scans candidate objects under a match context and uses geometry helpers. Treat it as a tri-state helper whose exact meaning depends on the caller, not a global boolean “success” flag.
- The `0x8FE890` call in that run-selector branch supplies the bearing to the current movement target, zero for two additional arguments, and `60` for a fourth argument. Inside the helper, a bounded draw from `[player + 0xB90] + 5` contributes to a candidate threshold; heading/vector helpers `0x8C3810`, `0x8C3850`, `0x8BC550`, and `0x8C7610` derive geometry used by the checks. It scans the player's team list at `[team + 0x534]` with count `[team + 0x568]`, excludes the current player, and reads teammate time, position, movement deadline (`+0x9C8`), and movement flag (`+0x9CC`). It also writes a derived value to global `0xDA9E74`. These are concrete inputs and side effects, but the three return values still cannot be named as “lane clear”, “receiver free”, or another tactical concept without dynamic validation.
- A fresh full decompilation of `0x8FE890` resolves more of that score. Its starting threshold is `200 - (([player+0xBEC]/2 + [player+0x348])*5)/2` when player flag byte `+0x882` bit 0 is clear; when set, it is `(Random([player+0xB90]+5)/3 + 20)*10`. A projected endpoint is built from a heading vector of magnitude `(arg*16)/10` and match offsets `+0x6D0/+0x6D4`. A candidate teammate's movement slack is `[teammate+0x9C8] - [teammate match+0xB0] - 1` when its deadline is still ahead and flag `+0x9CC` is clear; slack above 8 skips that candidate. The candidate score combines squared blended heading error divided by a player-derived denominator (floored to 25), `slack²*10`, and `[teammate+0x64]`. If this is no greater than the threshold, the helper returns 2; a post-scan endpoint inside the match-context rectangle returns 0, otherwise it returns 1. A teammate possession flag adds 600 to that candidate's threshold. The teammate-list ordering/field `+0x64`, match offsets, and return labels' tactical meanings remain unknown, so this is recovered arithmetic and branch behavior, not a named football rule.

Another caller at `0x934EA5` continues down its special branch only for return `2`. Those caller-specific effects still do not identify what the categories mean in match terms.
- In the run-selector branch around `0x9285BC`, the field at `[match + 0x6]` splits behavior at `0xD1` (209); its precise semantic name is unknown. The helper's result remains context-dependent, so this branch alone does not recover the full pass-ahead decision formula.
- The action processor at `0x92DF20` calls `0x8EB4E0` with the current action ID. The meanings of these player fields, the draw's consumer, and the `50` threshold units are not yet established.
- The observed shot path is `0x93181B → 0x94C0D0 → 0x94E980 → 0x94CBB0`. `0x94E980` repeatedly asks `0x94CBB0` for trajectory samples, increments a sample count at `+0x3EE8`, and stores values from `+0x3ED8`. ## Off-ball movement and interception

The player decision block around `0x93AE98–0x93B17A` contains live off-ball movement branches. It writes the chosen action at `[player + 0x8CC]`, movement target coordinates at `+0x8BC/+0x8C0`, and then joins the shared action path at `0x9468D0`.

- A separate team-state rebuild routine at `0x9603A0` is reached from tactical and higher-level update helpers. It walks each side's active-player array at team `+0x4CC` (count byte `+0x528`), keeps eligible players whose state byte `+0x8A6` is `1` and whose flags at `+0x882` have mask `1` clear, and builds one list per side. It sorts both lists with an inline comparator at `0x95DD60`: descending by `2 * [player + 0xBB0] + [player + 0xBE8]`, with `[player + 0x0C]` as a descending tie-break. It pairs equal ranks up to the shorter list, storing reciprocal player pointers in `+0xAF4` and `+0xAF8`. `0x964930` calls this rebuild during marker/tactical updates, including after injured-player processing; the main match routine `0x8D88F0` later reaches the per-player processor `0x8D59C0`, which reads `+0xAF8` in a time/flag gate. The nearby debug strings are `Initialised setup_markers`, `Done covering players`, and `Setup Markers etc`; this supports a coverage/marking role for the links but does not reveal the compared fields' football meanings. The rank inputs are populated by `0x8F8390`: `+0xBB0` uses `0x8EE170(0x34, 0x200008)`, whose base lookup `0x8EE0B0` reads player byte `+0x7F0`; `+0xBE8` uses attribute key `0x0F` in the ordinary path, with a `0x404021` mask observed, and the base lookup combines player byte `+0x7CB` with field `+0x8A4`. The first outer helper also applies context corrections and clamps the result. The stat labels and full branch-specific derivations remain unresolved. The demo now applies the recovered descending comparator and rank-to-rank pairing to its ten outfielders, but uses synthetic positioning/tackling inputs, shirt number as the tie proxy, and outfield-only eligibility; it does not reproduce the native attribute derivation or eligibility flags.

- One branch chooses `400` (`ME_MOVE_TO_BALL`). It first checks the match-context pointer at `+0x423F8`, a predicate at `0x8FA560`, team identity, and the values at player `+0x9B8` and match time `+0x64`. When that path is reached before time `20`, it asks `0x911840` for a state and stores the return value; `601` is explicitly treated as a special case. If the branch continues, `0x8C6080` is called with the player and match coordinates, the resulting index selects entries from global tables at `0xDA9E78/0xDA9E7C`, and the target is formed from the match coordinates minus those entries. It sets movement mode `4`. The table contents' semantic names and coordinate scale are unresolved.
- The interception branch calls `0x9048B0` with flags `0x100A` and output slots for two target coordinates plus an auxiliary value. The helper obtains the trajectory object through `[player + 0x68] + 0x68`, reads its sample base index at `+0x4` and count at `+0x8`, then scans 16-byte records beginning at `+0x58`, from the current match counter (or the next tick when flag `0x20` is clear) up to a context-bounded time. The first three dwords are copied to the caller's x, y, and auxiliary outputs for the selected record; flag-dependent branches inspect the third and fourth dwords. The best-score register starts at `2000`; an eligible candidate replaces it only when its accumulated score is lower. In the ordinary scoring arm the base is Euclidean distance through `0x8C65E0`; mask `0x4` adds absolute x separation from `[player + 0x80]`, while masks `0x1`, `0x2`, and `0x400` add separate context/reach/time adjustments. Other masks apply candidate-time, pitch-side, control-event, and record-metadata filters, though their tactical names are unknown. The selected record's absolute trajectory time is stored separately from the score. The helper's return is mode-dependent: with flag bit `0x2`, a randomized comparison may place a `0x8BC3C0` estimate in it; a no-candidate path with bit `0x8` set returns `-1`; other fallbacks can return a current match-time value. The caller stores this return at `[player + 0x8D0]`, so that field is not a universal trajectory index. In the calling movement branch, another estimate is computed through `0x8BC3C0`/`0x8C0420`, reduced by `2` when `0x8EE780` is true, then compared with the helper return; when match-context `+0x1EC` is not `-1`, the estimate is also bounded by that field. The scoring weights, meanings of several flags, and compared-value units remain partly unresolved.
- The reach filter `0x8BCF50` is now tied to the game's actual `ball_at_feet_offsets.mdt`. Loader `0x8CBdd0` reads 360 headings × 5 signed (x,y) pairs, and this helper indexes the first pair at `heading * 0x3C`. It subtracts that offset from candidate-minus-player coordinates, adds two shortest circular heading differences scaled by `15 / min([player + 0x60], 40)`, divides by `max(candidateTime - [match + 0xB0], 1)`, then applies strict `<10` for nonzero mode or `<30` for mode zero. The table's heading-zero offset is `(0,15)`, heading 90 `(15,0)`, 180 `(0,-15)`, and 270 `(-15,0)`. The threshold units and `[player+0x60]` meaning remain unresolved.
- For the active caller's flags `0x100A`, `0x9048B0` starts scanning at current match time + 1. In its ordinary flat-sample arm, mode-zero reach failure adds `200` to the distance score; when mode zero passes and the randomized `bVar2` branch is false, mode one then yields `(baseDistance - 100) / max(floor(scoreStep/2),1)` on pass, or `(baseDistance - 50) / max(floor((scoreStep-8)/2),1)` on failure, with signed integer truncation. This is only that deterministic scoring arm: trajectory height/metadata filters, the randomized `bVar2` path, timing/context masks, and the exact distance helper's rounding remain open. The demo now scans its discrete ball samples and applies this arm with the real 360-heading offset table, but coordinate mapping ×100, current move-target reference for native `+0x80/+0x78`, and turn-cap 20 for `+0x60` are explicitly proxies; it still cannot reconstruct the native eligibility flags or complete composite choice. The `flags & 2` random pre-gate is `R3 < ((signedByte(player+0x7BE) / 2 + 10) * R2 * R1)`, with bounded draws `R1=Random([player+0xB8C]+2)`, `R2=Random([player+0xB90]+5)`, and `R3=Random(100)`; equality does not set `bVar2`. A true gate stores `0x8BC3C0()` in `local_18`.
- One input to that comparison is now traced more precisely. `0x8BC3C0` computes `3 * (50 - [player + 0x30]) + 3/2 * ([player + 0x348] - penalty)`, where `penalty` is zero when `[player + 0xC0] <= 1600` and otherwise `(field - 1600) / 20` capped at `10`. If `[match + 0x6] >= 0xD7`, the result is capped at `30`. The caller passes this value with the candidate x/y coordinates and option `4` to `0x8C0420`, a wrapper around `0x8BD030`, then compares that path estimate with the mode-dependent return from `0x9048B0`. The fields, option, result units, and exact meaning of the return remain unresolved.
- Once a candidate passes those gates, an auxiliary output below `15` chooses `414` (`ME_MOVE_TO_INTERCEPT_BALL`); otherwise it chooses `452` (`ME_MOVE_TO_INTERCEPT_HIGH_BALL`). The target is adjusted using bearing helper `0x8BC550` and the same global side tables, then movement mode `4` is set. The planner also compares the third sample dword with thresholds including `10`, `15`, and `20`, and in one flag-conditioned path rejects records whose fourth dword is at most `15`. The `<15` split and these sample fields are consistent with a height/elevation test, but their exact source-field mapping and units are not proven.
- A separate branch uses predicate `0x8FA660` and helper `0x8C0990`; when its returned value is greater than `-40`, it writes an adjusted target and selects `403` (`ME_MOVE_ONSIDE`) with movement mode `0x10`. This is consistent with the action's embedded label, but the helper result, threshold units, and complete trigger conditions remain unresolved.
- The long movement-maintenance routine beginning at `0x9468F0` revisits states `400/401` and `414/415/452`, compares stored candidate values at `+0x8D0` with match time/counter fields, and can recompute targets through `0x94BF40`, `0x8BBAC0`, and `0x9048B0`. The same `0x9048B0` helper is called there with several other flag masks (`0x2065`, `0x20AA`, `0x2025`), showing that target prediction is shared by multiple movement paths. Exact flag meanings and the full update cadence remain unresolved.
- The player-position refresh path is distinct from the ball's 16-byte trajectory samples. `0x919EF0` sets a per-player update deadline at `[match + 0xB0] + duration` in `[player + 0x9C8]`, clears `[player + 0x9CC]`, and calls `0x918460`; when argument bit `1` is set, it also calls `0x8BBA10` and `0x904640`. That helper calls `0x8BBAC0` with the current match counter and output pointers for player fields `+0x48/+0x4C/+0x50/+0x54` and `+0xB8`. `0x8BBAC0` reads a separate 28-byte-stride motion record array at `[entity + 0x14]`: before endpoint time `[entity + 0x34]`, it selects a record using `max(requestedTime - [entity + 0x24], 0)`; at/after that time it outputs endpoint coordinates from `+0x38/+0x3C`. It compares selected x/y with the current x/y and returns a changed flag.
- The corresponding path builder is `0x8BD030`, reached from the movement-target wrapper `0x8C0420` and a convenience wrapper at `0x8BE410`. It derives a heading for the requested x/y through `0x8BC730` when needed, obtains direction components from `0x8C3810/0x8C3850`, and accumulates those components in 14-bit fixed-point steps. The heading difference is folded to the shortest signed turn in the 0–359 heading system. On the path gated by `flags & 0x280180`, requested movement magnitude is scaled by `min(100, field[+0x34C] - floor(abs(turn)*4/9) + 90 + field[+0x344])` percent, then floored at 30. Each generated tick rotates by at most field `+0x60` (with a separate goalkeeper/candidate path that derives a limit from `+0xBD0`), and one loop branch increases the per-tick step magnitude by the integer quotient `(90-min(remainingTurn, (15-field[+0x344])*6))*(field[+0x350]+8)*5/180` until it reaches the requested magnitude. These are exact arithmetic relationships in the decompiled path builder; the three player fields have not been mapped to named attributes, and the flag branches decide when each rule applies. The loop shifts accumulators right by 14 to form integer x/y samples, then copies seven dwords into `[entity + 0x14] + sampleIndex * 0x1C`; it also updates endpoint x/y at `+0x38/+0x3C`, heading at `+0x42`, and path start/end times at `+0x24/+0x34`. Thus movement is represented by a generated, timed list of discrete positions rather than by a render-frame velocity update. Each record stores x/y, a caller-provided byte at `+0x08`, the current step magnitude at `+0x0C`, heading at `+0x10`, and two additional dwords at `+0x14/+0x18` whose uses are not fully mapped. `0x8BBAC0` selects one of those samples by time; interpolation between samples has not been found.
- The native table source for the low-magnitude vector branch is now identified. `0x8CBF40` loads `distance_angle_table.mdt` as 360 headings × 100 magnitudes. Its payload is 36,000 pairs of signed 32-bit components after a 12-byte MDT header. For magnitudes `0–99`, `0x8C3810` and `0x8C3850` index that grid by `heading * 100 + magnitude`; the executable's in-memory component records use a 12-byte stride. Table rows confirm the heading convention: heading 0 points along positive y, 90 along positive x, 180 along negative y, and 270 along negative x. At magnitude `>= 100`, both helpers use a separate per-heading basis and integer scaling by 1/20; the exact source/meaning of that basis is still unresolved. This accounts for the movement-vector inputs without identifying the speed/attribute formula that chooses their magnitude.
- The sample reader is discrete rather than interpolated. Before endpoint time `[entity + 0x34]`, `0x8BBAC0` computes `max(requestedTime - [entity + 0x24], 0)` and reads that 28-byte record directly. It returns x/y plus the record's byte `+0x08`, dword `+0x0C`, word `+0x10`, and dword `+0x14` through caller-provided outputs. At or after endpoint time it returns the stored endpoint x/y at `+0x38/+0x3C` and endpoint metadata. The visible frame smoothing, if any, is outside this sampler; no interpolation inside the native position reader has been found.
- The ball-arrival resolver at `0x913BB0` was decompiled over its full body (`0x913BB0–0x914ADD`). `0x9468F0` calls it at a movement-state timing gate with an output pointer to `[player + 0x8C8]`, then writes the returned action to `[player + 0x8CC]`; the `+0x8C8` value participates in score/threshold calculations, but its field name is unresolved. The resolver returns `0` when the trajectory end time equals the current match counter; if a nonnegative trajectory end time is already before the current counter, it delegates directly to `0x911840`. - The lazy score/count builder `0x8FA9D0`, reached by accessors `0x8FC740` and `0x8C3320` when `[player+0x9BB]` is clear, scans the object list at `[player+0x70]+0x534` (count `[team+0x568]`) and excludes entries with `[entry+0x882]&1`. ## Ball trajectory state

- The action dispatcher routes `100` (`ME_NORMAL_PASS`) through `0x8BC0D0` and then `0x903840`; several related pass/header/clearance action IDs share that worker. It copies 17 dwords from match `+0x15C..+0x19C` into `+0x118..+0x158`, then calls trajectory initializer `0x94C0D0` and builder `0x94E980` with the outgoing-ball context. The copy maps source `+0x184` to flight `+0x140` (curve input), and source `+0x190` to flight `+0x14C` (designated-player pointer). That pointer is used in event and geometry checks, including side and position comparisons. A concrete producer is the kick-off branch of `0x938F60`, reached under an unresolved `0x8C78A0` predicate and match flag bit `0x400` at `+0x6C8`: it writes match `+0x190` to team `+0x538`, falling back to team `+0x534` if the first pointer is the current player, then sets context action `121` and dispatches it. The meanings of those two team fields and the generic-pass writer/selector remain unresolved. The demo now replays this action at opening kick-off, half-time, and after goals, using a midfield receiver as an explicitly inferred proxy for the unnamed team pointers. After building the path, the worker updates the match's active-player pointer at `+0x42408`, toggles involved players' `+0x8A2` ownership byte, clears the interception-candidate pointer at `+0x423F8`, snapshots current ball coordinates into match `+0x12C..+0x134`, and updates team possession counters. This establishes the pass execution and flight handoff, but not how pass candidates are scored or how path parameters depend on player/tactical attributes.
- `0x94C0D0` initializes a trajectory object from three supplied coordinate values, resets trajectory counters/flags, and copies the match counter at `[match + 0xB0]` into its initial time fields. When there is no explicit source object, a neighboring initializer (`0x94C130`) asks `0x8BBAC0` for a current position based on the match's active ball object before initializing the trajectory.
- `0x94E980` builds the time/position samples. It stores position records at 16-byte strides beginning at object `+0x58`, tracks sample metadata around `+0x3ED4/+0x3ED8`, and increments a count at `+0x3EE8`. A loop bounds its sample index to `0..999`; `0x94CBB0` also guards against an index reaching `1000`.
- The base segment initializer `0x94C500` sets 14-bit x/y accumulators, then computes straight per-sample velocity as `delta * trunc(0x4000 / duration)`. Its nonzero-curve branch constructs two control points near one-third and two-thirds of the segment and delegates to `0x94BB80`; continuation initializer `0x94C620` can continue from current fixed-point velocity or start another curved segment. The demo now generates visible samples with this recurrence and the extracted curve branch; duration and normalized-to-native coordinate scale remain prototype inputs.
- `0x94E980` derives its curve scalar from target planar distance and flight-context `+0x140`. The 17-dword copy in `0x903840` maps source match `+0x184` to that flight field. The scalar is zero if the input is zero or distance is below `80` (`0x50`); otherwise the base is `(distance * input) / match[+0xA0DA8]`, ramped by `(distance-80)/170` for distances below `250`, and used at full value from `250` onward. Initializer `0x9598D0` writes `133` to match `+0xA0DA8`.
- Selector `0x9234A0` writes source match `+0x184` on verified branches: for action contexts 106/114 it selects a sign by comparing opaque player fields `+0xC4C` and `+0xC50`, with magnitude `floor(Random(player[+0xBD0]+2)/4)`; for action 123 it uses `RandomRange(-2,2)` (`-2..1`); another observed delivery branch explicitly writes zero. The offsets and upstream branch gates are not semantically mapped. `0x94C500` constructs the signed curve using a perpendicular offset from the start/end vector; `0x94BB80` converts the controls into cubic finite-difference coefficients in Q14, and `0x94C7B0` advances position, velocity, and acceleration by one sample. The demo now uses this recovered curve math when its prototype cross gate selects a cross; the cross gate and opaque-field proxy for the input remain inferred. Height, spin, collision, and bounce remain incomplete.
- Shots use a second curve-input slot. For the default shot action `300`, one selector path in `0x9234A0` initializes match `+0x1C0` with `RandomRange(-2,2)` (`-2..1`); a later gate can replace it with `(Random(player[+0xBD0]+2) * 11) / 30` when `Random(10) <= 0x8E9890()` and match field `+0x6D8` is below a global floating-point value. The player field and global threshold meanings remain unknown. In `0x92DF20`, the shot-state family passes match `+0x1C0` directly as the curve argument to `0x94E980`. Curled-effort action `316` starts from `[player+0xBD0]/3+5`; its follow-up can randomize that value using opaque fields `+0xC4C/+0xC50`, then applies a sign gate at context `+0x1C5`. Its final curve value is capped at ±12, while non-316 shots can be narrowed to ±2 in a separate condition. The demo samples the observed base action-300 input branch; the overwrite gate and the other shot-type formulas are still unresolved.
- Each sample is a 16-byte record. `0x94E980` copies four dwords from an input record into the sample array; if it takes the fallback path, it writes the current three values and zeroes the fourth dword. The first three are reused as the trajectory's three position components; the fourth field's meaning is unresolved. The builder also calls helper `0x9748C0` with bound `10000`, optionally passes that result to a context callback, and stores it at `+0x3F08`; the draw's effect on path construction has not been traced.
- The sampling helper `0x94CBB0` computes an integer progress percentage from two time arguments and a duration: `(timeB - timeA) * 100 / duration`. It then selects and interpolates among stored samples using integer multiply/divide operations and Euclidean-distance checks through `0x8C65E0`; a requested record index reaching `1000` takes an error/assert path. In a verified branch, the first two dwords of 16-byte records are interpolated using the time difference between records, while heading helpers `0x8C3810/0x8C3850` contribute fixed-point directional increments in another branch. Some intermediate terms are shifted by `14` bits, confirming a `2^14` fixed-point component. Mode flags and trajectory/context fields gate these branches, and their physical meanings remain unresolved, so this is not enough to claim a particular gravity or height model.
- `0x8C3810` and `0x8C3850` take a signed 16-bit heading and a magnitude, fetch separate components from heading/speed tables, and scale the table result when magnitude is at least `100`. `0x94CBB0` passes the trajectory heading at context `+0x5C` and a computed scalar to both helpers, then adds their results into two output coordinates. This confirms direction-vector motion in the sampled path; how that displacement relates to the third position component and the fourth record dword remains unknown.
- The trajectory sampler `0x94CBB0` computes integer progress `(endTime-startTime)*100/duration`, accumulates x/y from the 14-bit fixed-point state, and writes x, y, height, and an auxiliary dword into 16-byte records. It also checks pitch edges and the goal mouth: the observed goal-line corridor is centered on context `+0x28` with `±0x28` bounds (plus a one-unit crossing tolerance), while height gates include `0x1F` and net/back-wall limits. Goal/post/crossbar paths set context flags at `+0x3EF0/+0x3EFC/+0x3F00`, store a reflected heading at `+0x3F04`, and alter the sample step and velocity before continuing. These constants and state changes are confirmed; their field names, units, and complete collision/bounce response remain unresolved.
- `0x94C230` scans the recorded time values at `+0x3ED4` and returns the first one that is not earlier than the current match counter at `[match + 0xB0]`; if no stored sample qualifies, it returns the current counter. This links the trajectory sample list to the live match timeline, although the duration unit and cadence are still unknown.

The native engine therefore keeps a sampled trajectory timeline that off-ball decision code can query. The prototype's straight pass/shot path and its animation duration remain illustrative approximations.

## Recovered action labels

The name resolver at `0x8F5BF0` maps action IDs to embedded `ME_*` labels through jump tables and compact byte remaps. The reproducible extraction in [`action-state-name-map.csv`](action-state-name-map.csv) contains 210 named ID/label pairs; [`extract_action_names.py`](extract_action_names.py) regenerates it from the matching executable. The resolver's fallback text is `UNKNOWN ACTION`. An absent ID in the CSV therefore means “no named label recovered from this resolver,” not proof that the number can never occur internally.

The map now gives exact examples across the engine: passes and clearances (`100`, `102–124`), on-ball states (`200–214`), shot types (`300–316`), player movement/marking/interception (`400+` selected IDs), contests and ball control (`600–709` selected IDs), goalkeeper actions (`800–809` and `1000+`), tackling/fouls (`900+` selected IDs), and set-piece positioning (`1100+` selected IDs). IDs are sparse; do not treat the displayed spans as continuous enums. These are formatter labels, not evidence that each state is reachable in every match situation.

## Geometry helpers

- `0x8BC550` derives a bearing from an object's x/y at `+0x48/+0x4C` toward a target. If both coordinates match, it returns the object's heading at `+0x50`; otherwise it quantizes the deltas and looks up a heading in a table. ## Selector trajectory reader (REA MCP, 2026-11-23)

### Trajectory writer (`0x8BD0A0`)
